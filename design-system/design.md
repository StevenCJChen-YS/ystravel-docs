發現本檔與程式碼不一致時，**先確認哪邊是對的再改**，並回頭更新本檔——不要默默讓兩邊繼續分岔。

### 0.2 Token 分兩層

- **Base（共用底層）**：字體、間距、圓角、灰階、語意色、密度、按鈕階層 → **全系統一致**。
- **Theme（各系統主題層）**：只有 `primary` 主色各系統覆寫 → 改一行 `vite.config` 即可。

業界（Shopify、Atlassian、Material）都是這個結構：共用一套底，各產品換主色。

### 0.3 動 UI 前的固定動作

1. 讀本檔對應章節
2. 查 §7 共用元件庫——**有現成的就用，不要重造**
3. 需要調整視覺 → 走 §12 的實作位置（theme seam），**不准 `!important` 或深層選擇器硬蓋**
4. 寫任何頁面前先問：**「第二個模組/頁也會用到嗎？」** 會 → 抽 `shared/ui/`；不會 → 放 `modules/<模組>/components/`

## 1. 設計原則

1. **後台導向、穩定可掃讀**：資料用表格（表頭＋分頁 footer）、建立/編輯開 modal 而非行內輸入、列操作用 icon 鈕。使用者熟悉的是 EIP/Vuetify 式後台。
2. **白卡浮灰底**：light mode 的卡片一定是白的，浮在灰底頁面上。
3. **規則定在共用層，不靠各頁記得**：任何「每頁都要記得貼」的規則遲早會漏。看到規則性問題就收斂到元件或 theme，不要在單一頁面貼補丁。
4. **Light / Dark 一起做**：禁止新增只支援 light mode 的硬寫色。
5. **能預防就不報錯**：最好的錯誤訊息是根本不會出現的錯誤（見 §8.3）。
6. **一個 view 只有一個最強 primary**。

## 2. 色彩

### 2.1 主色（Theme 層）

| 系統 | primary |
|---|---|
| **平台（Auth／入口網／各模組）** | **Teal** |
| CRM（未來若獨立主色） | Violet |
| EIP（未來） | 待定（不得與平台撞色） |

- 主色**不得使用任何語意色**，否則會與成功/警告/資訊訊息撞色。
- 換主色＝改 `vite.config` 的 `primary` 別名一行，全站走 semantic token 自動連動。

### 2.2 語意色盤（各系統一致，不覆寫）

| 語意 | 色 |
|---|---|
| secondary | sky |
| success | emerald |
| info | sky |
| warning | amber |
| error | rose |
| neutral | **light = gray／dark = zinc**（明暗混搭） |

灰階單一入口＝`neutral-*` 別名：light 家族由 `vite.config` 的 `neutral: 'gray'` 管、dark 家族由 `main.css` 的 `.dark` 重指整組 oklch 管。**換家族只動一處。**

### 2.3 明暗色階策略

**同一語意色在明暗用不同階**——白底對比偏低要**深一階**、深底要**亮一階**才跳得出來。

| 對象 | light | dark |
|---|---|---|
| 語意變數 `--ui-*`（`text-primary`／subtle・soft 標籤／focus ring／outline 主鈕） | primary(teal)、warning(amber) ＝**自訂 550 半階**；success／secondary／info ＝ 600；error(rose) 用預設 | **400** |
| **solid 主鈕**（固定色階，**明暗拆階**，2026-07-24 拍板） | `bg-primary-550` 白字（2.98，**刻意接受例外**見 §2.7），hover/active → **650/750** | `bg-primary-450` **深字** `text-neutral-900`（8.37 ✅），hover/active → **550/650** |
| **solid error 鈕**（固定色階，明暗一致，2026-07-24） | `bg-error-600` 白字（4.53 ✅），hover/active → 700/800 | 同 light |
| **switch checked**（固定色階，明暗一致） | `bg-primary-500` | 同 light |

> **solid 主鈕拆階的來龍去脈**（2026-07-24，取代 07-14「明暗一律固定 550」）：550 白字僅 2.98
> 未達 AA，本輪原意是修到達標——但過標的 light 候選 Steven 都嫌深（650＝4.59、700＝5.36 皆
> 看過實畫面後否決），**拍板「好看優先」維持 550、列刻意接受例外**（teal 亮階配白字物理上
> 到不了 4.5，見 §2.7）。dark 側則真正修好：700 明暗通用版對背景分離度腰斬（3.30）淘汰、
> 550 深字版 active 越按對比越掉（3.31）淘汰，定案**亮底深字**（Material／Nuxt UI 官方同路線，
> 官方 dark＝400 深字，我們取自訂 450 半階稍飽和）。最終梯度＝**「半階位整步跳」：
> light 550→650→750、dark 450→550→650，dark 就是 light 整體亮一階**。各組合數字見 §2.7。

**自訂半階的做法**（Nuxt UI `--ui-color-*` 別名只內建 50–950）——**兩套別名都要接**，缺一不生效
（例外：650 只當 utility 用、沒被 `--ui-*` 引用，接 ① 即可）：

```css
@theme {
  --color-teal-450: oklch(74.05% 0.146 182.2);    /* oklch 插值取 400/500 中間（主鈕 dark base） */
  --color-teal-550: oklch(65.2% 0.129 183.604);   /* oklch 插值取 500/600 中間 */
  --color-teal-650: oklch(54.6% 0.105 185.8);     /* ⚠️ 非中點：中點白字 4.41 差 0.09 不過 AA，取「最淺過標點」＝4.59 */
  --color-teal-750: oklch(47.4% 0.087 187.3);     /* oklch 插值取 700/800 中間（主鈕 light active） */
  --color-amber-550: oklch(71.75% 0.1835 64.199);
  --color-primary-450: var(--color-teal-450);      /* ① Tailwind utility 用（bg-primary-450） */
  --color-primary-550: var(--color-teal-550);
  --color-primary-650: var(--color-teal-650);
  --color-primary-750: var(--color-teal-750);
  --color-warning-550: var(--color-amber-550);
}
:root {
  --ui-color-primary-550: var(--color-teal-550);   /* ② Nuxt UI --ui-primary 引用用 */
  --ui-color-warning-550: var(--color-amber-550);
}
```

> ⚠️ `--ui-*` 未分層寫在 `:root` 會洩漏到 dark，故 `.dark` 要補回 400 抵銷。

### 2.4 表面層級（2026-07-24 重訂，取代原「中性底色分層」）

**全站只有三層表面，一律引用 token，禁止各頁再寫 `dark:bg-neutral-8xx`（§13-25 擋件）：**

| Token | 用在哪 | light | dark |
|---|---|---|---|
| `--app-surface-page` | AppShell 內容區底（卡片後面那層） | neutral-100 | neutral-950 |
| `--app-surface-card` | 卡片（`SurfaceCard`）、殼件（header／drawer）、modal | `#fff` | neutral-800 |
| `--app-surface-inset` | 卡片**裡面**的區塊（帳號中心的內卡等） | neutral-50 | neutral-900 |

用法：`class="bg-[var(--app-surface-card)]"`。定義在 platform `apps/portal/src/assets/css/main.css`。

**為什麼重訂**：原本 850／950 被混用在不同語意上（850 同時當卡片、深色表頭、modal；
950 同時當內容區底與欄位），實測結果是**全站其實只有一個表面層級**——
三層容器套疊時色值完全相同，「內卡 vs 外卡」明暗兩邊都是 **1.00（逐位元同色）**，
巢狀讀起來只是邊框在疊；卡片對頁面也只有 light 1.05／dark 1.17。
連帶症狀：輸入框與內容區底同為 neutral-950，卡片上的欄位看起來像被打了一個直通頁面的洞。

**相鄰層分離度（真實元件實測）**：

| | light | dark |
|---|---|---|
| card vs page | 1.05 → **1.10** | 1.17 → **1.34** |
| inset vs card | 1.00 → **1.05** | 1.00 → **1.19** |

> **light 拉不高是物理限制**，近白表面之間擠不出明度差——淺色靠的是邊框與陰影，
> 不要為了追數字把淺色頁面底壓深。淺色的層次感主要來自「內卡不與外卡同色」這個結構修正。

**規則**：

1. **`inset` 不可直接疊在 `inset` 上**（會退回 1.00 的老問題）。需要再深一層＝回來重新檢討層級。
2. **⚠️ token 一律引用 `--ui-color-neutral-*`，不可用 `--color-neutral-*`**——後者明暗都是 gray、
   從未被重新指向，只有前者會在 `.dark` 被換成 zinc。寫錯的話深色會變成帶藍調的 gray
   （實測 `rgb(3,7,18)`），違反 2026-07-11「dark 走 zinc 免得偏 navy」的拍板，
   **而且淺色完全正常、不會被發現**。
3. **井底層（輸入框／`TableFrame`／`OrderManager`）刻意不納入這三個 token**，維持 light 白／dark `neutral-950`：
   ①它與 page 同值可接受——兩者永遠不相鄰（井底一定在卡片內、page 一定在卡片外）
   ②`TableFrame` 的斑馬紋在 dark 正是 `neutral-900`，把框底改成 `inset(900)` 斑馬紋會直接消失。
   原本「欄位像挖了個洞」的觀感，卡片提到 800 後井底對卡片拉到 1.34，就會讀成刻意的凹槽。
4. **表格 thead 是深色標題帶、不是表面層**，維持 light `neutral-700`／dark `neutral-850`；
   斑馬紋偶列 `bg-muted`（dark `neutral-900`，對框底 1.12）。

> Nuxt UI 原生的 `bg-default`／`bg-muted`／`bg-elevated`／`bg-accented` 仍用於**狀態**
>（hover、選取態、active nav、卡內次層帶），但**表面層級一律走上表三個 token**。
> ⚠️ 卡片不要用 `bg-elevated`：light 的 `bg-elevated` 與頁面底同值，卡片會糊進頁底（2026-07-10 實測）。

**狀態底色在 dark 整體推一階（2026-07-24，跟著表面層級一起調）**：

| token | 官方 dark 值 | 本站 dark | 對卡片分離度 |
|---|---|---|---|
| `bg-muted`（凹一層） | 800 | **900** | 1.000 → **1.189** |
| `bg-elevated`（浮一層） | 800 | **700** | 1.000 → **1.428** |
| `bg-accented`（選取態） | 700 | **600** | 1.428 → 1.929 |

**為什麼**：卡片改成 `neutral-800` 之後，官方 dark 的 `bg-muted` 與 `bg-elevated`
**本來就都是 `neutral-800`**——於是它們在卡片上變成**逐位元同色**，三個狀態階裡有兩個失去語意。
症狀：稽核詳情的原始資料區整塊看不見；拖曳區 hover 是官方的 `hover:bg-elevated/25`，
方向等於「朝卡片的顏色靠過去」，**越 hover 越融合**。
`accented` 必須跟著推，否則會跟新的 `elevated` 撞在 700。改後 `hover:bg-elevated/25`
疊在卡片上＝分離 1.086（hover 本來就該微妙）。**這張表只動 dark。**

> ⚠️ **更正（2026-07-30）：本條原本寫「light 沒有這個問題」——那是錯的**，而且與上面
> 第 167 行自己寫的「light 的 `bg-elevated` 與頁面底同值」正面打架。
> **light 有同一個病，只是換了位置**：dark 撞的是**卡片**，light 撞的是**頁面底**——
> `--app-surface-page` ＝ `neutral-100` ＝ `bg-elevated` 的 light 值，**逐位元同色、分離 1.000**。
> 這句錯話讓同一個病因躲過三次：①2026-07-10 卡片糊進頁底（只寫成告誡）
> ②2026-07-28 骨架在 light 整頁看不見（改成單獨給骨架一個 `neutral-200`，見 §8.1-7）
> ③2026-07-30 工作日曆的 ghost 外部連結鈕 hover 前後零變化（Steven 從畫面回報）。
> **修的是這句話，不是色階**——見下方 §2.4.1 的判準與實測範圍。

> ⚠️ **不能只改用到的那幾頁**：`hover:bg-elevated` 是 **Nuxt UI 元件內部**在用的
> （拖曳區／下拉選項／選取 pill／排序鈕…），逐頁貼補丁救不了，而且會製造一批散落的硬寫色。
>
> ⚠️ **狀態 token 不可拿來當表面用**（§13-32 擋件）。`UserIdentityCard` 的 hero 名片與
> 稽核原始資料區原本就是這樣寫的，2026-07-24 已改走 `--app-surface-*`。
> 判準：**這塊東西會不會因為 hover／選取而改變？** 不會＝表面，走 `--app-surface-*`。

#### 2.4.1 直接坐在頁面底上的控件，hover 不可用 `bg-elevated`（2026-07-30 定案）

**light 的 `bg-elevated` ＝ `--app-surface-page`（分離 1.000）**，所以任何**不在卡片裡**的控件，
只要 hover 走官方預設的 `hover:bg-elevated`，light 下就是**零回饋**——不是「很淡」，是完全不變。
改用 **`hover:bg-accented`**（對頁面底 1.125）。

**適用範圍很窄，別為它動全域 token。** 2026-07-30 實測四頁（工作日曆／使用者管理／
跨模組選項／員工管理），符合「ghost 或 outline ＋ 直接坐在頁面底上」的控件**全站只有一顆**
（工作日曆的政府辦公日曆表鈕）。原因：**幾乎所有互動元素都住在卡片裡**（`hover:bg-elevated`
疊在白卡上＝1.101，看得見），而 `PageHeader #actions` 以外沒有裸在頁面底上的控件；
其他頁的 header 動作鈕都是 primary solid，`TableCard #toolbar` 裡那幾顆 outline 都在卡片上。

> **曾經評估並否決的做法**：把 light 的 `bg-elevated` 推到 `neutral-200`、`bg-accented` 跟到
> `neutral-300`（＝dark 那次的對稱做法）。數字是對的（頁面底上 1.000→1.125、白卡上 1.101→1.238），
> **但實測代價是全站每頁 1～5 個元素靜止就變色**——avatar 預設底、`UBadge neutral soft`
> （部門／狀態標籤）、分頁的當前頁鈕。**為一顆鈕動全站，投報率不對。**
> ⚠️ 這條的教訓不是「別改共用層」，是**先數清楚分子**：當時的推薦建立在「light 到處都在痛」
> 的假設上，逐頁量完才發現只有一處。

**改在哪一層**：改**共用元件**（本站是 `ToolbarButton`），不寫在使用點（那是上面警告的散落硬寫色），
也不改全域 theme（會連 navbar 收合鈕、月曆月份切換等 ghost 鈕一起變明顯，單一頁就 7 顆）。
判準：**這個修正該跟著「哪一類控件」走？** `ToolbarButton` 的定位正是「工具列／頁首動作鈕」，
就是會坐在頁面底上的那一群。

⚠️ **只改 light**：dark 沒有這個病（頁底 `neutral-950`、`bg-elevated` 已推到 `700`），
`dark:` 那半把官方值原樣寫回去，靠 `.dark` 祖先選擇器的較高特異性蓋回來，深色與 aurora 逐像素不變。
⚠️ **這條在觸控裝置上不生效**——手機沒有 hover。要讓手機也看得出可點，得動**靜止態**
（改 `outline`，或 `link` 變體的 `text-muted` → hover `text-default`），那是另一個決定。

#### 2.4.2 hover 底色該用哪一階（2026-07-30 定案）

起因：Steven 從畫面回報「rail 的模組鈕 hover 好像比右邊的頁面按鈕深」。實測他是對的
——light 下三者**都坐在白底上**，卻是三個深度，而且背後沒有規則：

| 元件 | hover | 選取／active | 對白底分離度 |
|---|---|---|---|
| rail 模組鈕（改前）| `bg-accented` | `bg-primary/10` | **1.238** ← 最深 |
| navbar 動作鈕（搜尋／收件匣／收合）| `bg-elevated` | 無 | 1.101 |
| 側欄頁面連結（官方 `navigation-menu`）| `bg-elevated/50` | `bg-elevated` | 1.052 ← 最淺 |
| `ListItemButton` | `bg-elevated/50` | `bg-elevated` | 1.052 |

**規則（一條軸）：hover 的深度取決於「這一階要不要留給選取態」。**

1. **選取態也用灰階**的清單／導覽 → hover **半階** `bg-elevated/50`（1.052）、
   選取**整階** `bg-elevated`（1.101）。差的那半階就是「暫時指著」vs「目前在這」。
2. **選取態用品牌色**（rail ＝ `bg-primary/10`）**或根本沒有選取態**（navbar 動作鈕）
   → hover 直接用**整階** `bg-elevated`（1.101），**不必讓階**。
3. **控件坐在頁面底上** → 往深一階 `bg-accented`（1.125），見 §2.4.1。

**照這條規則只有 rail 要改**（`accented` → `elevated`，1.238 → 1.101）。
`bg-accented` 在 §2.4 的表裡標的是**選取態**，rail 拿選取態的階去做 hover 是誤用。

> ⚠️ **這條規則第一版是錯的，寫下來避免重演**：原本的結論是「三個全部收斂到 1.101」，
> 包含把側欄的 `elevated/50` 提到 `elevated`。**那會讓側欄的 hover 與 active 變成同色**
> ——使用者就分不出「目前在哪一頁」和「滑鼠正指著哪一頁」。
> 病因是**只量了想改的那個屬性（hover），沒問「這個變體原本還帶了什麼」（active）**
> ——與 2026-07-28 徽章 `variants.size` 那次同一個錯法。
> **可複用：要改一個狀態的色階之前，先把同一個元件的其他狀態一起列出來。**

> **佐證：aurora 早就分對了**——rail 用 `--aurora-hover`（白 8%）、側欄用
> `--aurora-hover-soft`（白 6%），差半階，正是規則 1／2 的區分。**只有 light 沒跟上。**

⚠️ **rail 這條與 §2.4.1 不同，明暗都改**：§2.4.1 是 light 專屬的病（dark 的頁底與 elevated
本來就分得開），而「拿選取態的階當 hover」是**與模式無關的誤用**，plain dark 同樣中招
（改前 2.295 → 改後 1.699，改後與 navbar 同階）。**aurora 不受影響**（`aurora:` 選擇器更具體）。

### 2.5 文字灰階

一律用 semantic token，下表 light 值供對照（dark 由 token 自動翻低階變亮）：

| 階層 | token | neutral 階 | light 值 | 用途 |
|---|---|---|---|---|
| 主文字 | `text-highlighted` | 900 | `#101828` | 標題 |
| 標籤/內文 | `text-default` | 700 | `#364153` | 欄位標籤、內文 |
| 說明 | `text-toned` | 600 | `#4a5565` | 輔助句 |
| 淡化 | `text-muted` | 500 | `#6a7282` | placeholder、次要連結、提示 |
| 更淡 | `text-dimmed` | 400 | `#99a1af` | 最弱提示、角標 |

#### 2.5.1 說明類文字：色階／字級／長度一起訂（2026-07-27 定案）

上表講的是「這個 token 長怎樣」，不足以決定**一段說明文字該用哪一階**——
`toned`／`muted`／`dimmed` 的字面描述（說明／提示／最弱提示）邊界模糊，
於是同一種東西在不同頁各憑感覺：頁面副標曾經一頁 `muted` 一頁 `toned`
（Steven 2026-07-27 直接從畫面上看出深淺不一）。

**判準是「這段文字長在哪個結構位置」——看 markup 就有答案。**

| 結構角色 | 色階 | 字級 | 長度與 RWD |
|---|---|---|---|
| **頁面副標**（h1 下） | `text-muted` | `text-sm` | ≤20 全形字、`<sm` 隱藏、`≥sm` `line-clamp-1` |
| **區塊副標**（h2/h3 下、卡片 header 內） | `text-muted` | `text-xs` | ≤20 全形字、`<sm` 隱藏、`truncate` |
| **區塊內說明段**（獨立成段、卡片 footer note、提示條內文） | `text-toned` | `text-xs` | **不限長、不隱藏、不截斷** |
| **Modal 內文** | `text-toned` | `text-sm` | 不隱藏 |
| **表格／清單的次要資料欄** | `text-toned` | 跟表格 | — |
| **meta**（時間戳、IP、計數、placeholder） | `text-muted` | `text-xs` | — |
| **空值 `—`、附屬代碼、裝飾性圖示**（chevron／拖曳把手／ⓘ） | `text-dimmed` | — | — |

> **這張表的每一列，色階與字級是一起訂的**——這是刻意的，見下面「為什麼不用重要性」。

**為什麼判準不是「使用者需不需要讀它」**（2026-07-27 初稿用過這條，當天就被 Steven 推翻）：

1. **主觀。** 寫那段字的人幾乎一定認為「需要讀」，否則他不會寫。這條在實務上會退化成
   「作者覺得重要就用 `toned`」，等於沒有規則。
2. **它會把兩個原本獨立的軸綁在一起。** 字級（§3.2）是照**結構角色**訂的
   （Body/Help 固定 `text-sm`、Meta 固定 `text-xs`），色階若改照**重要性**訂，
   兩套判準交叉就必然出現：某段被判「必讀」（重要性軸）→ 但它結構上是 Meta（字級軸）
   → 兩軸打架 → 只好開例外。**例外會一路長出來，而根因是判準選錯了軸。**

   Steven 的原話：「因為你覺得這三個地方的說明很重要 所以你給他提升到 toned，
   但是現在因為提升後 又要改大小？我不確定這樣下去會不會有很多例外或是問題。」

**「副標比 Modal 內文更淡」乍看反直覺，照這張表卻是對的**——副標只負責定位，
Modal 內文是要你據以做決定的。

**這張表也解掉「說明太長」那類爭論**，同樣不靠主觀判斷：

- **長度限制只綁在副標上**（頁面／區塊副標 ≤20 字）。「區塊內說明段」不限長——
  例：LINE 綁定的個資告知「我們只取得用於推送的識別碼，不會讀取您的聊天內容…」
  它**不是副標**，所以不受 20 字限制，也不隱藏、不截斷。
- 一段說明在手機上讀起來很雜時，先確認它的結構角色。**如果它是說明段卻被塞在副標的位置，
  那是版位問題不是字數問題**——解法是給它自己的版位，不是砍字。
- 反過來，**副標超過 20 字就是超過，不留例外**（Steven 2026-07-27）；
  多出來的機制說明搬去 tooltip／說明段（同 §10.4）。

**互動元件的靜止色不走這張表**（導覽項目、圖示鈕的 `text-toned`）——那是元件狀態不是說明文字，判準在 §8.1。

### 2.6 邊框

`border-muted`（一般分隔線/卡片）／`border-toned`（需更明顯）／`border-accented`（強調/選取）。

### 2.7 對比度基線（2026-07-24 首度實測定案）

標準＝WCAG AA：**一般文字 4.5、大字與 UI 元件 3.0**。
量測法＝computed style → 畫進 canvas 讀 sRGB → WCAG relative luminance。
**對比是 sRGB 純數學、與螢幕無關**——換螢幕看起來深淺不同是面板體感，數字不會變；
「同一頁兩個螢幕數字不同」＝其中一邊是舊版頁面，先重新整理。

> 要在近白底上拿到 4.5，文字就必須是真的深色。這與 solid 鈕（深底白字）是相反的問題，
> 不能拿 solid 的色階直覺套過來。

**刻意接受的例外**：

- **solid 主鈕 light base（白字 on teal-550）2.98**：過標候選 650／700 Steven 看過實畫面後
  均嫌深，拍板好看優先（2026-07-24）。teal 亮階配白字物理上到不了 4.5——這是品牌色的
  已知代價，**不得**引用本例外去開新的不及格組合（新組合仍走規則 1）。
- **`text-dimmed` 2.60**：拉高會破壞 §2.5 五階層次。限最弱提示、角標；不得承載必要資訊。
- **switch checked teal-500 對白底 2.42**：開關狀態由**滑塊位置**表達，顏色是冗餘線索。
- **focus ring（`--ui-primary` 550）對白底 2.98**：差 3.0 線 0.02，現階段接受；日後動 `--ui-primary` 時順手校正。

**規則**：

1. **新做任何「語意色 solid 鈕」前先過上表**——白字達 4.5 才准上；不夠就換深階或改深字，不准硬上。
2. **amber 永不配白字**（2.61）；warning 若需 solid 鈕一律深字。
3. success／info 目前無 solid 鈕；要新增前先量。
4. **`text-primary`（550，對白底 2.98）限強調色／標籤用途，不得當正文連結色**——正文超連結要另尋達 4.5 的方案。
5. **soft／subtle 一律「light 文字 700 階＋dark 維持 400 階」**，規則收在 `vite.config.ts` 的
   badge／alert／button theme（`SOFT_TEXT` 一張表），**不准逐頁貼 class**。新元件若也吃
   `bg-{color}/10 text-{color}` 這組官方預設，補進同一張表即可。
6. **新增自訂半階一律取「最淺過標點」，不是數學中點**——`--color-teal-650` 就是這樣來的
   （中點 L55.55% 白字 4.41 差 0.09 不過，往下取 L54.6%＝4.59）。**同名 token 只能有一套推導邏輯**：
   要補 emerald／amber／sky／rose 的 650 就得照這條規則現場量，不可用插值省事
   （2026-07-24 曾評估補齊四色 650，因只有 error 過標＋推導邏輯會分裂而作罷）。

### 2.8 分類色票（非語意用色，2026-08-07 定案）

**用途**：讓使用者維護的**分類**彼此分得開——目前唯一使用者是 CRM 客戶標籤
（最頂層節點挑一個色，底下所有子孫共用）。

⚠️ **這一節與 §2.2 語意色盤是兩件事。** 語意色回答「這是什麼狀態」（成功／警告／錯誤），
分類色只回答「這是哪一群」——**它不承載任何語意**，換一個色不改變意思。

**七個色**（Tailwind 原生色相，不自訂半階）：

| 色 | 色相角 | light 對比 | dark 對比 |
|---|---|---|---|
| `orange` | 47.6° | 4.69 ✅ | 5.32 ✅ |
| `lime` | 130.9° | 4.65 ✅ | 7.72 ✅ |
| `cyan` | 215.2° | 4.82 ✅ | 6.79 ✅ |
| `blue` | 259.8° | 6.07 ✅ | 4.81 ✅ |
| `purple` | 303.9° | 6.21 ✅ | 4.58 ✅ |
| `fuchsia` | 322.2° | 5.47 ✅ | 4.93 ✅ |
| `pink` | 354.3° | 5.17 ✅ | 4.67 ✅ |

**推導完全沿用 §2.7 規則 5**，沒有新規則：
底色 `bg-{color}-500/10`、框 `/25`、文字 **light 700 階／dark 400 階**。
所以它也該收進 `vite.config.ts` 的 `SOFT_TEXT` 那張表，不准逐頁貼 class。

⚠️ **要加新色進來的人先看這條**：新色**同時要進 `ui.colors` 與 `theme.colors`**，
兩個設定各管各的（前者產變數、後者才產 soft／solid 等變體的 class），只加前者的症狀是
**文字有色、底色全透明，而且什麼都不會報錯**；而 `theme.colors` 是**取代不是合併**，
既有的六個語意色必須一起列，否則全站徽章與按鈕會一起失去樣式。
事故經過與驗收方法見 [ui-conventions.md](./ui-conventions.md) §21。

**沒設色的分類一律 `neutral`**——§6.3 已把 neutral 定義成「非啟用但一切正常」，
沒挑顏色正好是這個語意，不另外發明。

#### 為什麼是七個不是八個

湊到八個時，**一定會有一個新色貼著某個語意色**（實測：最好的八色方案瓶頸是
`amber ↔ yellow` 16.0°，次佳是 `emerald ↔ green` 12.9°）。
七個的瓶頸是 `purple ↔ fuchsia` **18.3°**——**落在兩個新色之間**。

**差別不在角度大小，在瓶頸落在哪**：新色彼此像，只是「兩群標籤顏色接近」；
新色像語意色，就會有人每次看到黃標籤都多想一次「這是不是待處理」。
**分類色不該讓人聯想到狀態**，這是它與 §2.2 的分工。

#### 被淘汰的兩個

| 色 | light | dark | |
|---|---|---|---|
| `indigo` | 7.12 ✅ | **4.13 ❌** | 深色模式文字不夠亮 |
| `violet` | 6.42 ✅ | **4.48 ❌** | 差 0.02 |

⚠️ **兩個都可以靠「dark 改用 300 階」救，但不救**——§2.7 規則 6：
**同名 token 只能有一套推導邏輯**。為兩個色開例外，下一個人就不知道該照哪套算。

#### 量測方法（可重跑）

oklch 值取自 `node_modules/tailwindcss/theme.css`（規格值，不是 app 的 build 產物），
在瀏覽器用 canvas 轉 sRGB 後套 WCAG relative luminance。
**算法先用 §2.7 已驗的三個數字校準過**：emerald 4.76／4.73、sky 5.16／5.13、rose 5.20／5.21，
全在 0.03 以內才拿去算新色。

> 📌 **新增分類色的做法**：從 Tailwind 原生色相裡挑，先算它與**五個有彩度的語意色**
> （teal／sky／emerald／amber／rose）以及既有分類色的色相角距，再照上面的推導算明暗兩組對比。
> 灰階（gray／zinc）**不參與色相比對**——它們的 chroma 只有 0.016～0.027，靠彩度就分得開，
> 拿它們的色相角去比會把 blue、slate 這些誤判成撞色。

## 3. 字體排印

### 3.1 字體堆疊

```
--font-sans: "Microsoft JhengHei", "微軟正黑體", "PingFang TC",
             "Noto Sans TC Variable", "Noto Sans TC", "Segoe UI",
             ui-sans-serif, system-ui, sans-serif;
--font-mono: "JetBrains Mono", "Cascadia Code", "SFMono-Regular", Consolas, monospace;
```

**全系統字、零自架中文 webfont**：Win 微軟正黑體、Mac 蘋方，其他平台自架 Noto 保底。

> ⚠️ **不要再提議自架中文 webfont 追求多字重**。自架 webfont（Noto／台北黑體／Inter）在 Windows 無 hinting 一律糊，系統字有 hinting 最清晰（2026-07-13 完整試錯驗證）。

### 3.2 字級

| 用途 | 大小 |
|---|---|
| Page title | mobile `text-xl`，`sm+` `text-2xl` |
| Section title | mobile `text-base`，`lg+` `text-lg` |
| 卡片內區塊標題 | `text-[15px] font-semibold`（帳號中心慣例） |
| **Body / Help / 定義列** | **固定 `text-sm`** |
| Meta / code / timestamp | 固定 `text-xs` |

**密集資訊流條目**（通知收件匣等「一格三行」的 feed 型 UI，2026-07-23 新增）：

| 條目層 | 大小 |
|---|---|
| 條目標題（類別，如「人事異動通知」） | `text-sm font-semibold` |
| 條目內文（事實句） | `text-[13px]` |
| 條目時間戳 | `text-xs` |

> 13px 只准用在 feed 條目內文這類「同格內要與 15px 標題拉開兩層」的密集場景，
> 不得拿去縮一般 Body（一般內文仍固定 `text-sm`）。

**響應式縮放原則：大字才縮、小字不縮。** 大標題（28px+）小螢幕可降一~兩階；body/說明（14~16px）與小字（12px）已在可讀性底線，**不隨斷點縮小**。

> ⚠️ 唯一放大到 16px 的地方是**手機的輸入控件**（見 §6.2），那是 iOS 限制不是排版選擇。顯示文字不要跟著放大。

### 3.3 字重

**系統中文字只有兩檔粗細**：微軟正黑體 400/700、蘋方無 700，跨平台交集＝ **400（細）／700（粗）**。

**CSS 字重匹配有方向**（關鍵，別誤判）：`font-medium`(500) 往**下**靠 400、`font-semibold`(600) 往**上**靠 700。

**規則：標題／需強調 → `font-semibold`；一般內容 → `font-normal`；避免 `font-medium`。**
（medium 對系統字＝400 視覺無效；混入西文 webfont 時還會造成同排「英文粗、中文細」的斷層。）

**墨量實測（2026-07-24，微軟正黑體，canvas 數字元覆蓋的像素比例）**——把上面的結論變成數字，
日後再問「那用 medium 呢」直接看表結案：

| | 400 | 500 | 600 | 700 |
|---|---|---|---|---|
| 中文 14px | 1.00 | **1.00** | 1.168 | **1.168** |
| 中文 12px | 1.00 | **1.00** | 1.174 | **1.174** |
| 英文 14px | 1.00 | **1.00** | 1.155 | **1.155** |

- **500 與 400 的墨量完全相同**（比值 1.000）＝ `font-medium` 是 no-op，不是「差一點點」。
- **600 與 700 渲染結果一致**（都吃到同一個 Bold 字面）→ 需要粗體時一律寫 `font-semibold`，不用 `font-bold`。
- **Bold 相對 Regular 只多約 17% 墨**——「400 跳 700」聽起來很大，實際的視覺跳躍比想像小。

> 起因：dark solid 主鈕改成「亮底深字」後 Steven 覺得字看起來變細。
> 那是 **irradiation（光暈效應）**——亮底上的暗字邊緣被光侵蝕、看起來較細，暗底上的亮字則外溢顯粗，
> 所以同一字重在明暗兩種底色下本來就不等重。**2026-07-24 拍板維持 400 不加粗**（Steven 看過並排後
> 認為 Bold 太粗）；對比 8.37 遠超 AA，這純粹是觀感、沒有可讀性問題。

層次不只靠字重——善用字級（§3.2）＋文字灰階（§2.5）＋間距（§4.1）。

### 3.4 介面縮放（字級三檔，2026-07-29）

使用者可在**帳號中心→個人化**把全站字級調成三檔。實作＝`apps/portal/src/assets/css/main.css` 的 `--fs`
＋`shared/composables/useInterfaceScale.ts`（比照主題：localStorage 每台各記，待 `auth-user-preferences` 才上帳號）。

| 檔位 | `--fs` | `html` 屬性 | `text-sm` 實際 |
|---|---|---|---|
| 標準 | 1（預設） | **不掛屬性** | 14px |
| 大 | 1.15 | `data-font-scale="large"` | 16.1px |
| 特大 | 1.3 | `data-font-scale="xlarge"` | 18.2px |

**核心原則：只縮字，不縮間距。**

`--fs` 乘進 Tailwind 的 `--text-*`（連 `--line-height` 一起，行高才跟著長、字不會擠），
**`--spacing` 刻意不動**。所以放大後縱向會稍長（字大了躲不掉），但**橫向密度完全守住**。

> 為什麼不做等比例放大：那是瀏覽器 `Ctrl` `+` 已經在做的事，而它正是問題——字大的同時間距、
> 留白、圖示全部膨脹，一頁能看的列數掉一大半。**「字大但版面不膨脹」是瀏覽器做不到、
> 自己做唯一的價值**（Steven 2026-07-29：「這種系統本來資訊就很多，弄那麼大字根本塞不了東西」）。
> 也因此本功能**不是**密度切換（Gmail 舒適/緊湊、Salesforce Comfy/Compact 調的是間距不是字級），
> 兩者別混為一談。

**寫新 UI 時的三條規則：**

1. **一律用 named 字級**（`text-sm` 等）——它們自動吃 `--fs`。
2. 真的需要寫死 px 時（§3.2 允許的 13/15px 等），**必須寫成 `text-[calc(15px*var(--fs))]`**，
   否則該處會是全站唯一不跟著放大的字，一調檔位就露餡。
3. **不該縮的東西別縮**：固定尺寸容器裡的數字（如通知徽章 9px 在 17px 圓點內，跟著放大會撐破）、
   純裝飾性文字（登入頁的英文標籤）。判準是「**它是內容，還是版面元件的一部分**」。
4. **第 2 條也適用於 Nuxt UI 自己的 theme**（2026-08-10 補）——官方有好幾個元件的尺寸表
   就是寫死 px，掃自己的程式碼掃不到它們。發現時**在 `vite.config.ts` 的元件 theme 覆寫**
   （鐵則 4：視覺調校走全域 theme），連**行高一起乘**：官方的 `/3` ＝ `calc(var(--spacing)*3)`，
   而 `--spacing` 刻意不縮，只放大字級會讓字擠在原本的行框裡。

> ⚠️ **這一條是漏掉了才補的。** 2026-07-29 做這個功能時第 2 條**只掃了我們自己的程式碼**
> ——app 內至今只剩 6 處寫死 px，而那 6 處全是第 3 條明文豁免的（登入頁裝飾字、通知鈴鐺）。
> **沒有人掃過 vendor 的 theme**，於是 badge 的 `xs`／`sm`（`text-[8px]/3`、`text-[10px]/3`）
> 一直不跟著縮放，**全站 33 個使用點**都吃這個虧，2026-08-10 由 Steven 從畫面上發現
>（platform PR #177）。`md` 以上是 named 的 `text-xs` 所以一直正常，這也是它拖了十二天沒被看到的原因。
>
> 📌 **`chip` 刻意不改**（通知鈴鐺的數字）——那正是第 3 條講的「固定尺寸容器裡的數字」。
>
> 📌 附帶一條可複用的事實：**tailwind-merge 認得 `text-[calc(…)]` 屬於字級這一組**，
> 會把官方的 `text-[10px]/3` 正確消掉（實測）。這與 §4.2 記的 `rounded-xsm` **不同**
> ——半階圓角它不認得，兩個 class 都留著、靠 CSS 順序贏。**覆寫前不要假設哪一種，去量。**

⚠️ 標準檔**不掛 `data-font-scale` 屬性**（走 `--fs` 預設 1），確保沒調過的人看到的畫面與本功能上線前逐像素一致。

## 4. 間距、圓角、斷點、密度

### 4.1 間距（8 點網格）

- 所有間距用 **4/8 的倍數**（8、16、24、32…），不用 10、18、22 這類亂數。
- **親疏原則：群組內 8px、群組間 24px**——用距離表達「誰跟誰一組」。
- 響應式：小螢幕收攏**結構性留白**——**桌機 24 四邊；`<md`（768）頁面外距與卡片內距都收成
  左右 12／上下 16**（`px-3 py-4 md:p-6`／`p-6 max-md:px-3 max-md:py-4`）。
  **節奏性間距（8/24）不縮**，縮了層次就亂；**垂直節奏（列的 `py-3`/`py-4`）也不動**。
  📌 兩者刻意同一組數字、同一個斷點：手機上「螢幕邊→卡片邊」與「卡片邊→內容」對稱，左右合計 24。
  ⚠️ **完整理由與例外**（卡片自己不留內距、改由子層貼邊的版型怎麼收）在
  `apps/portal/src/shared/ui/layout/SurfaceCard.vue` 檔頭——**那裡是唯一說明處，這裡只記數字**。
  （2026-08-14 隨 platform #210 更正；原本寫的「頁面外距 24→16、卡片內距 32→20~24」是收斂前的舊值。）

### 4.2 圓角（2026-07-28 改版）

**唯一來源＝`main.css` 的 `--ui-radius: 0.25rem`**，全站刻度由它推導（倍率是 Nuxt UI 定的
0.5x / 1x / 1.5x / 2x / 3x）：

| 階 | 值 | 用在 |
|---|---|---|
| `rounded-xs` | **2px** | 徽章 xs、tooltip、tabs 的 trigger 記號 |
| **`rounded-xsm`（半階）** | **3px** | **徽章 sm 以上、控件 xs**（按鈕／input／select／textarea）|
| `rounded-sm` | **4px** | 卡片內的小區塊、控件 sm、選單「選項」高亮 |
| `rounded-md` | **6px** | 控件 md（＝全站預設控件高 36px 那階）、**浮層**（UserMenu／各式選單／popover）、**表格框** |
| `rounded-lg` | **8px** | 控件 lg、卡片、清單外框、彈窗／slideover |
| `rounded-xl` | **12px** | 控件 xl（僅登入頁）、帳號中心大卡 |

**要整體調整圓角就只動 `--ui-radius` 那一行**——半階也是 `calc(var(--ui-radius) * 0.75)`，會一起等比例走。

#### 半階 `rounded-xsm`（2026-07-30 Steven 拍板）

3px 不在 Nuxt UI 的倍率上（xs 是 0.5x＝2px、sm 是 1x＝4px）。徽章與 xs 控件落在
**2px 太銳利、4px 又太圓**的位置——2px 讀起來像反鋸齒的毛邊而不是刻意的形狀。
先例＝色階早就有半階（`teal-450/550/650/750`、`neutral-850`），同一個理由：官方刻度太粗。

命名 `xsm`＝xs 與 sm 之間。**刻意不叫 `2xs`**（那會讓人以為比 xs 更小，方向剛好相反）。

> **⚠️ 為什麼要寫成 `@utility` 而不是改 token：** Nuxt UI 的 `ui.css` 用 `@theme default inline`，
> **`inline` 代表 Tailwind 把「值」編進 class**，不是編成 `var()` 參照——實際產出是
> `.rounded-xs { border-radius: calc(var(--ui-radius) * 0.5) }`，那個 `0.5` 寫死在 class 裡，
> **`--radius-xs` 從頭到尾沒有被任何東西參照**（實測：把 `--radius-xs` 設成 3px，徽章仍是 2px）。
> 所以「新增一階」只能從 utility 這一層做。定義在 `main.css`。
>
> **⚠️⚠️ 已知副作用（實測）：tailwind-merge 不認得 `rounded-xsm`**，不會把它跟官方
> `rounded-md` 視為同一組衝突類別，所以套用半階的元件身上**兩個 class 都會留著**
> （徽章實際是 `rounded-md rounded-xsm`）。它能贏靠的是 **CSS 順序**（自訂 utility 排在內建之後），
> 不是類別合併。後果：在使用點寫 `<UBadge class="rounded-lg">` 想蓋掉圓角會**靜默失效**。
> 這與下面「不准在使用點蓋」同向所以可接受，但它是**無聲**的失敗——要改圓角請改該元件的 theme。

> **⛔ 不准再寫 `rounded-[任意值]`。** 若發現「刻度上沒有我要的值」，那是**元件該站哪一階**
> 的問題——去改該元件的 theme 挑另一階，不要繞過刻度。
>
> **唯一容許的例外是巢狀圓角**：內圈套在外圈裡面時，內圈要略小才看起來同心
> （現存一例：`NotificationPanel` 的 tabs indicator 7.2px 套在 8px 的 list 裡）。
> 例外要在原地寫明理由，否則下一輪巡檢會有人「順手統一」掉。

#### 4.2.1 巢狀圓角：內圈比外圈**小一階**（2026-07-31 補寫，規則早就在跑）

**卡片內的帶框容器，圓角一律取外圈的下一階**，不要各自挑：

| 外圈 | 內圈 | 實例 |
|---|---|---|
| 一般卡片 `rounded-lg` 8px | **`rounded-md` 6px** | 表格身（`TableFrame`）、順序管理（`OrderManager`）、分機表的公司資訊（皆走 `InsetFrame`）|
| 帳號中心大卡 `rounded-xl` 12px | **`rounded-lg` 8px** | 個人化／通知設定／帳號安全／個人資料的各區塊、LINE 綁定（皆走 `InsetPanel`）|

> **這條是「補寫」不是「新訂」**——2026-07-31 全站量過一輪，除了兩處以外**本來就全部照這個走**。
> 沒寫下來的代價是它看起來像「四種圓角各自為政」，於是差點被當成「該統一成同一個值」來改
> ——**那樣反而會把對的規律改掉**。**規則不寫下來，正確的東西也會被誤判成髒亂。**

- **不要靠數學算同心**：內距 24~25px 遠大於圓角，嚴格同心公式會推出 0。這是**觀感**規則——
  外圈 8 配內 6（差 2）、外圈 12 配內 8（差 4），兩者都經 Steven 看過畫面。
- **差 0 就是錯的**：個人資料頁曾經內外都是 12px，**實測差 0**，畫面上完全看不出那是內縮區塊。
- 內圈**給不給底色**是另一條判準（見 §2.4 與兩個元件的檔頭註解）：
  裝有分列機制的內容（斑馬紋表格）**不給底**——底色會吃掉「奇數列＝卡片白、偶數列＝`bg-muted`」
  的對比；沒有分列機制的區塊**要給底**才跟卡片分得開。**兩者不可互換，也不要順手統一。**

#### 為什麼要立這條規則（2026-07-28 的代價）

`--ui-radius` 原本是 `0.375rem`（3/6/9/12），而**那不是任何人挑的值**——
`main.css` 的註解寫著「試 0.375rem（Steven 視覺驗收中）」，從 Phase 1 搬進來掛了兩週沒被驗收。

更嚴重的是**它已經是孤島**：按鈕／輸入框／select／textarea 的圓角被硬寫成
`rounded-[0.125~0.625rem]`，完全不吃這個變數。當初有人發現刻度推不出想要的值，
選擇繞過去而不是修它。於是只剩徽章、卡片、浮層還在用 token——那正好就是後來被指出「太圓」的地方。

**同一個病灶在徽章上重演了一次**：官方預設圓角太圓，於是全站 **34 處**
`<UBadge class="rounded-xs">` 手動蓋掉它，散在 14 個檔案、連 `shared/ui/` 的共用元件都在寫。

> **判準：同一個補丁抄超過兩三次，就不是「大家各有偏好」，是預設值錯了。**
> 回頭改共用層，不要在每個使用點貼補丁——61 處補丁（27 圓角＋34 徽章）就是這樣長出來的。

### 4.3 斷點與驗收基準寬度

`base <640` / `sm ≥640` / `md ≥768` / `lg ≥1024` / `xl ≥1280` / `2xl ≥1536`

**驗收基準寬度（2026-07-24 Steven 定）**：

| 寬度 | 要求 | 說明 |
|---|---|---|
| **375px** | **完整驗收——要好看、不擠、不裁切** | 手機的驗收基準。iPhone SE／13 mini 的邏輯寬，現行最窄的常見機型 |
| 320px | 只要求**不出現水平捲動**，不要求好看 | `main.css` 的 `body { min-width: 320px }` 是防線 |
| ≥1280px | 桌機驗收 | |

**UI 改動的驗收＝桌機與 375px 各看一次**（2026-07-23 選項樹事故：只看桌機、數字漂亮就當完成，
手機實際是兩層巢狀捲動）。**不要用「把元素寬度鎖成 375px」來模擬**——Tailwind 的 `sm:` 斷點
看的是**視窗寬度**，元素縮小不會觸發單欄，量到的東西全部無效（2026-07-24 踩過，
中文被逐字拆行、兩欄一直開著）。要真的把視窗調到 375。

**375px 要看的兩件事**：

1. **無水平捲動**（`document.documentElement.scrollWidth > innerWidth`）
2. **沒有元素的右緣超出容器內容框**——⚠️ **不能用 `scrollWidth > clientWidth` 驗**，
   元素會自己撐大、兩者永遠相等（見 §5.5.1）

> **「剛好塞得下」＝不合格。** 量到內容寬與可用寬相等（零餘裕）就要當成會壞——
> 不同裝置的字體渲染差一點點就翻車。2026-07-24 個人資料頁的 email 正是
> 「375px 下恰好 197px vs 可用 197px」，我的環境剛好過、Steven 實機被切掉。

### 4.5 密度

| 場景 | 尺寸 |
|---|---|
| 登入頁（品牌特例） | `xl` |
| 管理後台 mobile/tablet | `lg` |
| 管理後台 desktop | `md` |
| 列內操作鈕 | `sm` |
| Badge 預設／代碼型 badge | `sm`／`xs` |

#### 4.5.1 觸控目標：手機上「要用手指點的東西」最小 40px（2026-07-29 定案）

**判準是「這東西要不要用手指點」，不是「它是什麼元件、什麼尺寸」。**
控件的 `size` 講的是視覺密度，跟手指多粗無關——`sm` 的「每頁筆數」照樣是用手指點的。

| 對象 | 手機（<640px） | 桌機 | 寫在哪 |
|---|---|---|---|
| 輸入控件觸發器（input／select／selectMenu） | 40px | 36px | `vite.config` 各元件 `base`（`h-10 sm:h-9`）|
| **選單／下拉的「選項」** | **40px** | 32px（不變）| `vite.config` 三個選單的 `item` slot（`max-sm:min-h-10`）|
| icon-only 鈕 | 40px（`max-md:size-10`）或 36px（`max-sm:p-2.5`）| 照 §4.5 | 使用點（見 §6.1 三問）|
| 分組標頭、說明文字 | **不放大** | — | 它不可點，撐高只會讓人以為可選 |

三個選單＝`select`／`selectMenu`／`dropdownMenu`，規則寫在 `item` **slot** 而非 `size` 變體
——放變體等於宣告「小尺寸控件的選項可以難點」，而那不成立。
實測 `sm` select 的觸發器 28px、選項 40px，正是原生 iOS picker 的做法。

⚠️ **斷點要跟著同一顆控件的觸發器走**。三個選單的觸發器是 `h-10 sm:h-9`（<640px 才 40px），
所以選項也用 `max-sm:`。觸發器與選項用不同斷點，會做出「觸發器已縮回桌機尺寸、
選項還是手機尺寸」的中間態——沒有任何寬度會需要那個組合。

> **這條的由來值得記**：觸發器手機 40px 很早就訂好了（`vite.config` 裡就寫著
> 「手機 16px/40px 好點」），但**選項一直是官方預設的 32px**。
> 「點得開、選項卻難點」這個落差存在很久，而且不會有任何東西報錯——
> 直到 2026-07-29 把使用者管理的列動作收進 ⋯ 選單、實際去量了才發現。
> **同一條規則只套用在控件的一半，比完全沒套更難察覺**：因為「有訂規則」這件事本身，
> 會讓人不再去量。

**明文例外——列動作 `⋯` 維持 26px，等實機驗證（Steven 2026-08-04 拍板）：**

`RowActionsMenu`（表格每列最右的 `⋯`）在 375px 是 **26×26**，低於本節的 40px。
用在**員工管理／使用者管理／名片背景素材庫**三頁。

**先不修，等 `platform-cd-pipeline` 完成、正式部署到 VPS 之後，用真的手機開開看再決定。**
理由：26px 是不是真的難點，**devtools 量不出來**——它量的是 CSS 像素，
而手指點得準不準取決於實體尺寸與螢幕 DPI。同類前例：UDrawer 在 Windows 顯示縮放下文字會糊，
那是「桌面 devtools 模擬手機的假象、真機正常」（見 `FilterPanel` 檔頭）。

⚠️ **這是已拍板的暫緩，不是漏掉的**——巡檢時不要當擋件退件，也不要主動提議修。
⚠️ `SavedFilterMenu.vue` 目前那句註解把它寫成「**待辦**（見 PR 描述）」＝舊狀態，
**下次動到那個檔案時順手改成「等實機驗證後再定」**並寫明為什麼要等實機。

**實機驗證那次一併看**：「我的篩選」下拉選項（44px）、抽屜 footer 的存鈕（36px），
以及浮層捲動鎖修復在真的 iOS/Android Safari 上乾不乾淨（vaul 的 body 鎖在 iOS 行為跟桌面不完全一樣）。

#### 4.5.2 hover 才出現的動作＝在觸控裝置上不存在（2026-08-14 定案）

**判準：一個動作如果只有 hover 才看得見，它在手機上就是沒有這個功能。**
更糟的是用 `opacity-0` 藏——**`opacity: 0` 不擋點擊**，於是它變成「看不見卻點得到」的隱形地雷。

| 做法 | 判定 |
|---|---|
| 靜止態就看得見（可以很淡），hover 只是**加強** | ✅ 預設做法 |
| **狀態指示器兼任控件**——狀態與控制同一個位置，不用多一顆鈕 | ✅ 只有單一動作時最省 |
| 收進列尾的「⋯」選單（表格列動作範式）| ✅ 動作多於一個時 |
| 只有 hover 才出現，靜止態什麼都沒有 | ❌ 手機上等於沒有這個功能 |
| 用 `opacity-0` 藏起來但仍可點 | ⛔ 最差：使用者會點到卻不知道自己點了什麼 |

⚠️ **真的只想給桌機的東西，要讓它在觸控裝置上點不到**（`pointer-events-none`，或 `sm:` 才渲染）
——藏起來卻點得到，比沒有還糟。

⚠️ **靜止態的形狀要讀得出「可以點」，不能只讀得出「現在是什麼狀態」。**
2026-08-14 收件匣先做成空心圈（理由是「它的角色是狀態」），Steven 一看畫面就說
「長得像圓點不是信封」——**空心圈講得出狀態、講不出動作**，等於問題只解了一半。
換成淡信封（那本來就是「標未讀」這個動作的圖示）才成立。
📌 這一題**紙上論證不出來，一律看畫面**。

> **實例**（platform #225→#226，收件匣單筆標未讀）：已讀＝淡信封（動作）、
> 未讀＝實心點（狀態——點整列本來就會標已讀，那顆點不需要長得像按鈕）；
> hover 仍交叉淡化成信封，**桌機長相不變**。觸控目標手機 40／桌機 28（§4.5.1）。

**已知還沒收的**：`ToolbarButton`（靜止態的可點性）、`RowActionsMenu` 26px（等上面那次實機驗證一併看）。

### 5.2 頁面骨架

列表頁固定長這樣：

```
PageHeader → TableCard → DataToolbar → 深色表頭 UTable → TablePaginationFooter
```

回饋走 toast；危險／切換類動作走 `useConfirm`。

#### 5.2.1 麵包屑最後一層放什麼（2026-07-29 定案）

**最後一層只放「你打開的那個東西」的名字，不重複頁面名稱。**

```
組織管理 › 永信台北          ← 不是「組織管理 › 部門管理」
角色管理 › 人資管理者        ← 不是「角色管理 › 人資管理者 的權限設定」
使用者管理 › 陳阿傑          ← 不是「使用者管理 › 陳阿傑 的權限覆寫」
```

三個理由：

1. **麵包屑正下方的 H1 已經寫了這是什麼頁**，再寫一次是贅字，而且手機版更容易折行。
2. **只寫頁面名反而會弄丟關鍵資訊**——「組織管理 › 部門管理」看不出是**哪一間公司**的部門，
   多分公司的情境下等於沒說。
3. 業界慣例同此：前面幾層是「地方」，最後一層是「物件」（GitHub `owner / repo / issues`、
   Jira `Projects / MyProject / Issues`）。

物件名還沒載入時退回頁面名當 placeholder（`userName || '權限覆寫'`），
避免載入中出現一個空的麵包屑段。

#### 5.2.2 詳情頁：頁首什麼時候可以放進卡裡（2026-08-10 定案）

**預設仍然是頁首在卡外**（§5.2 的骨架），全站 17 個 `PageHeader` 有 16 個是這樣。
**只有一種情況可以把它包進卡裡：頁首本身開始承載「跟著這個對象走」的內容。**

目前唯一的使用點是 **CRM 客戶詳情**：

```
SurfaceCard
├ 識別區（px-5 py-4，border-b）  姓名＋稱謂＋標籤＋編輯鈕
└ px-5 py-4
  ├ UTabs（pill，w-fit）
  └ InsetFrame → 分頁內容
```

**判準：那塊東西是「這個對象是誰」，還是「這一頁叫什麼」？**
標題是後者（所以裸著沒問題）；標籤是前者——它描述的是這個人，跟你在看哪個分頁無關。
一旦頁首裡有前者，它就不再只是標題，而是一塊內容，而**這套視覺裡的內容住在卡片裡**。

放進 `PageHeader` 的 `#below-title` slot（選用，其他頁不給就不顯示）。

> ⚠️ **決定性的理由是極光模式，而它在淺色下完全看不出來**（Steven 2026-08-10 切到極光才發現）。
> 標籤 chip 是 `bg-{色}/10`——**10% 透明**。頁首裸著時它往上**每一層都是透明的**，
> 那 10% 直接疊在極光背景上，而**極光是漸層**：同一頁上方是亮青綠、下方接近黑。
> 於是 chip 清不清楚**取決於它落在頁面的哪個位置**——那不是一個可以調的數字。
> 卡片給了 `--aurora-panel`（45% 深色＋24px 模糊）當底，那 10% 才有東西可以疊。
>
> 📌 **可複用的一般規則**：**任何半透明底色的元素，都不該直接坐在極光背景上**——
> 它需要一層不透明或高不透明度的底。淺色與一般深色模式下這個問題不存在
>（那兩者的頁面底是單一色），所以**只驗淺色會漏掉它**。
>
> 📌 先例不是新發明：**帳號中心個人資料頁整頁沒有 `PageHeader`**，
> 直接用一張大名片（`ProfileHeroCard`）當頁首。那一頁走得更遠，本節是比較輕的版本。

**分頁內容包一層 `InsetFrame`**（外框、內縮、淺色不給底色）。
⚠️ **是 `InsetFrame` 不是 `InsetPanel`**——後者明暗都給 `--app-surface-inset`（灰底），
兩者的差別是刻意的（見該元件檔頭），別順手統一。`DefinitionList` 自己沒有外框，
套進來不會雙重邊框；圓角照「內圈比外圈小一階」（卡 8px → 框 6px）。

#### 5.2.3 詳情頁識別區的內部排法：三條規則（2026-08-11 定案）

§5.2.2 定的是「頁首什麼時候可以放進卡裡」，這一節定**那塊識別區裡面怎麼排**。
三條都是從同一次 375px 實測長出來的（客戶詳情、7 顆標籤）：

| 375px 識別區總高 | 之前 | 之後 |
|---|---|---|
| 標準字級 | 148px | **108px** |
| 大 | 192px | **143px** |
| 特大 | **208px** | **150px** |

> 208px ＝ **在看到任何一筆資料之前先吃掉四分之一個手機畫面**。
> ⚠️ **桌機 1430px 三個字級都是 1 排、60～73px**——這是純手機問題，
> 三條規則裡只有第 ② 條分斷點，另外兩條各寬度都適用。

**① 「跟著對象走」的內容跨整個寬度，不與右上角動作鈕共欄**

`PageHeader` 的 `#below-title` 在**標題列外面**，不在左欄裡。

⚠️ **理由是量出來的，而且反直覺**：右上角動作鈕吃掉 52px（鈕 40 ＋ gap 12），
左欄只剩 257px，而卡片內部有 309px——**但動作鈕只佔最上面那 40px**，
標籤第二排起早就過了它的下緣，卻還是被壓在 257 裡白白讓出空間。

> 📌 **可複用的一般規則：只佔頂部一行高度的東西，不該壓縮整欄的寬度。**
>
> ⚠️ **放寬到 309 之後標準字級一排都沒少**（差 3.7px 過不去，維持 3 排），
> 真正受益的是大與特大。這一句要留著——它是「心算以為會少一排、去量才發現沒有」的實例，
> 沒量的話會推薦一件在預設字級下完全沒有效果的事。
>
> 📌 順帶讓 `PageHeader` 原本那段 `items-start`／`items-center` 的特例消失了
>（`below-title` 在左欄裡會把左欄撐高、動作鈕跟著沉下去；搬出來之後固定 `items-center`
> 就與其餘 17 頁一致）。

**② 識別區的 chip 手機要收合，桌機不收**

`<sm` 收成 N 顆 ＋ **可點的**〔⌄ +N〕，`≥sm` 全部顯示（`CustomerTagChips` 的 `collapseBelowSm`）。

- **為什麼只收手機**：桌機三個字級都是 1 排，收了等於平白藏資訊
- **為什麼預設 3 顆**：**3 是標準字級一排放得下的實際容量**，不是湊出來的數字——
  留 3 顆在標準與大字級都是 1 排（跟留 2 顆一樣），只有特大要多付一排
- **展開之後不自動收回**（換一位對象、改完資料回來都維持展開）：使用者展開＝
  他明講「我要看全部」，而自動收回會讓他**看不到剛加的那一顆**
- **切換鈕接在 chip 列尾端，不另起一行**——另起一行自己就多佔一排
  （375px 實測 24px），把收合省下來的高度又吃回去
- **chevron 收合朝下、展開朝上**；icon 用 `size-3`(12px)，**不是 `md` 徽章預設的 `size-4`(16px)**
  ——16px 比徽章自己 12px 的文字還大
- ⚠️ **加 icon 的代價要知道**：大字級因此從 1 排變 2 排（113→143px），標準與特大免費。
  真的想要回 1 排，現成的折衷是「只有展開狀態帶 chevron」（收合狀態純 `+N`），成本為零

⚠️ **「靜態截斷」不算收合**：只顯示前 N 顆而看不到其餘的那種 prop，
從加上去到 2026-08-11 為止全站零使用——**「看得到但收起來」才是實際需要的行為**。

**③ 動作鈕不可以與資料 chip 放在同一個 wrap 容器**

上下兩塊（`flex flex-col gap-3`）：上面是「這個對象身上有什麼」＝**資料**，下面是**動作**。

⚠️ **不是因為它們長得像，是因為位置不穩定。** 兩者同在一個 `flex-wrap` 容器時，
**chip 只有 1～2 顆時那顆動作鈕會真的跑進 chip 那一排**
（375px 實測：2 顆時 chip ＋展開鈕＋動作鈕全部同一排），chip 多了才換行。
**時而同排、時而換行**——分不出資料與動作的原因是這個，
不只是「同高 24px、同圓角、間距只差 4px」。

- 間距 **12px 不是 8px**：chip 彼此是 4px，8px 只差一級，分不出層級
- 動作鈕 `self-start`（不要被拉成整行寬的按鈕）
- chip 那塊刻意**撐滿寬**——它內部的 `flex-wrap` 要有正確的可用寬度才算得出該在哪裡換行

### 5.3 篩選範式（選錯會改到行為，不只改版面）

**判準是「這頁的篩選是即時查還是套用才查」，不是螢幕寬度。**

| 模式 | 篩選鈕何時出現 | 用在哪 | 前提 |
|---|---|---|---|
| 預設 | `<md` | 條件 ≤4 的即時篩選頁（使用者、角色） | 平鋪版在 `≥md` 排得下 |
| `inline-from="2xl"` | `<2xl` | 條件 5 個的即時篩選頁（員工管理） | 平鋪版要 1536 才排得下 |
| `always-visible` | 所有寬度 | 搜尋為主、**套用才查**的頁（稽核） | 沒有平鋪版 |

- 前兩種是同一件事的兩個斷點（平鋪版存在、只是排不排得下）；`always-visible` 是另一回事。
- **不要把 `inline-from` 套到「套用才查」的頁**——平鋪版沒有套用鈕，等於每動一個下拉就掃一次大表。
- `FilterPanel` 本身 RWD 分流：`<sm` 底部 `UDrawer`／`≥sm` `UModal`。草稿流程由頁面持有：`@open` 拷真值進草稿、`@apply` 才寫回。
- **動作鈕分兩層**（2026-07-24 依實作校正原「一律貼著表格」的說法）：
  ①**頁面主要動作（新增／匯入等）→ `PageHeader` 的 `#actions`**（標題同行右邊，用 `ToolbarButton`）——全站一致（使用者、角色、工作日曆皆此擺法）。
  ②**列內／表格層的 CRUD（每列編輯刪除、欄位顯示、調整順序）→ 貼著表格**（`DataToolbar #actions` 或列尾），別把這些堆到頁首。
  （原文「動作鈕不要放頁首」易被讀成「連主要動作都不能放頁首」，與 roles/users 現況不符，故校正。）

**條件多到排不下時，先量再決定斷點**——用 `getBoundingClientRect` 量工具列那一列的寬度與 `top`（`top` 出現兩種值＝已經換行了），別憑感覺挑。

### 5.3.1 工具列的左右分組（2026-07-25 定案）

**一句判準：這個控件改變「看到哪些資料」，還是「對資料或呈現做事」？**

| 類別 | 例子 | slot | 位置 |
|---|---|---|---|
| **縮小資料範圍** | 搜尋、篩選鈕、篩選下拉 | `#filters` | **靠左**（緊接搜尋） |
| **對資料或呈現做事** | 匯出、調整順序、全部收合／展開、欄位顯示 | `#actions` | **靠右** |
| **頁面主要動作** | 新增、匯入 | 不進工具列 | **標題同行右邊**（見 §5.3 第 ① 條） |

「全部收合」「欄位顯示」歸 action 不歸 filter，因為它們改的是**呈現方式**不是資料集合——
收合起來的資料還在、篩掉的資料不在。這條界線剛好等於**「會不會影響匯出結果」**。

> **⚠️ 以前放錯 slot 看不出來。** 舊版兩個 slot 最後都被推到右邊，選錯沒有視覺後果；
> 2026-07-25 改成按功能分組後才現形，一口氣冒出一批。Review 時「這顆鈕放哪個 slot」
> 現在是有標準答案的（§13-33）。

**適用範圍＝走 `DataToolbar` 的表格工具列。**

- **日曆導覽列不套**：月份 prev/next/今天 是**導覽**不是篩選，業界慣例（Google Calendar）
  就是導覽靠左、視圖控制靠右。硬套會變成全部靠左、右邊整片空白。
- **不要手刻工具列版面**（§13-34）。稽核紀錄曾自己刻了一份與 `DataToolbar` 逐字相同的結構，
  結果整輪改動它一點都沒吃到——2026-07-25 已改用共用元件。

**區塊層級小標題的細則**：`OptionsManager` 這種「一個頁面裡多個區塊、各有自己小標題」的版面，
主要動作（新增）**`≥sm` 放工具列、`<sm` 才上移標題列**——桌機一列裝得下，硬拆成
「標題列一顆鈕＋工具列剩兩顆」會變成兩列各空一半；手機時 `ToolbarButton` 已收成
40×40 icon-only、佔位小，上移剛好把工具列的寬度讓給搜尋。
判準是**「標題列會不會只為了一顆鈕而存在」**。

> ⚠️ 顯隱掛在**外包的 `<span>`** 上，不要把 class 傳給 `ToolbarButton`：它是
> `inheritAttrs: false`、根元素是 `UTooltip`，class 只會落到內層 `UButton`，
> 外層 tooltip 仍然佔位、flex gap 會多出一格看不出原因的空隙。

**收合式篩選一定要配 chip 列**（`DataToolbar` 的 `#chips`）：`篩選 (N)` 只說有幾個、
不說是什麼，沒有它「為什麼只有 2 筆」會變成常態困惑。chip 可個別移除＋全部清除；
`<md` 整排不顯示（手機上多吃一整列，數字已足夠提示）。
⚠️ **「套用才查」的頁**（稽核）移除 chip 不能只清值——要自己回第一頁並重打 API。

### 5.3.2 「我的篩選」：哪一頁該有、哪一頁不該有（2026-08-04 定案）

**判準：這一頁篩選面板裡的條件有 3 個以上 → 接；2 個以下 → 不接。**

理由：「我的篩選」本身要花兩個動作（開清單、挑一組）。**條件只有 1–2 個時直接選比較快**
——加了不是多給一個功能，是讓人多繞一次路。

**例外往上**：條件只有 2 個、但其中一個**要打字搜尋才找得到**（如職稱字典 40 筆），也算。

拿 2026-08-04 的五頁現況照這條判過，**全中**：

### 5.4 表格

- **外觀一律抽 `vite.config` 的 `table` theme**（深色表頭、列高、內距），不逐頁寫 `:ui`。
- **欄寬＝auto 佈局＋百分比 th**（名稱/說明欄不設寬、拿剩餘），**勿加 `table-fixed`**——會鎖死 100%，多開欄位互相硬擠疊字。配 `TableCard` 的 `overflow-x-auto` 自然橫向捲動。
- **RWD 藏欄走 `useResponsiveColumns`**，別逐欄寫死 `hidden md:table-cell`；搭 `ColumnVisibilityMenu` 可手動加回，同一份 `columnVisibility` 綁 UTable。
- Nuxt UI 的 `UTable` **沒有內建 density prop**，要舒適/精簡切換得自綁兩組 padding。
- 可排序的表頭**一律走 `useTableSort` composable ＋ `sortableHeader()` helper**（見 §5.4.1），不各頁自刻 sortKey/accessors；底層按鈕＝`TableSortButton`（button theme 的全域 `font-normal` 會蓋掉 th 字重，helper 內已補回）。

### 5.4.1 表格欄位排序（sort，2026-07-24 新增）

> ⚠️ 名詞：這裡是 **sort（升降冪）**，跟 §5.5 的 order（人工序位）是兩件事。
> 一張表**兩者擇一**：有拖曳序位的表不給 column sort（否則點欄位排序會蓋掉你排好的序位）。

**哪些欄位可排序＝按型別自動推導，不必逐頁討論**（只標例外）：

| 欄位型別 | 預設 | 理由 |
|---|---|---|
| 名稱／文字識別、日期／時間、數字／量 | ✅ 可排序 | 掃描、找最近/最大很常用 |
| 單一狀態／enum（在職、啟用…） | 🟡 **有專屬篩選就不給**（能篩就不排） | 避免篩選與排序做同一件事 |
| 操作欄、頭像/icon 欄、多值欄（角色/標籤清單） | ❌ 不給 | 無語意順序或無單一排序鍵 |
| 有人工拖曳序位（order）的表 | ❌ 整表不給 column sort | 與序位語意衝突（見上方 ⚠️）|

**機制＝全站一套 UI、資料綁定分兩種**（`apps/portal/src/shared/composables/useTableSort.ts`）：

- **前端分頁的表**：`const sort = useTableSort(() => filtered.value, accessors)`，把 `sort.sorted` 接在**分頁切片之前**（`sort.sorted.value.slice(...)`）；欄位定義寫 `header: sortableHeader('姓名', 'name', sort)`。三段循環：升→降→取消。
- **後端分頁的表**（員工、稽核）：同一個 `sortableHeader` UI，但把 `sortKey`/`sortDir` 餵給 API 的 `orderBy`／`orderDir`，**不做前端排序**（前端只排得到當頁＝錯的）。
- accessor 回傳字串走 `localeCompare('zh-TW')`、數字比大小；空值給 `''` 或 `0`。

### 5.4.2 列內操作欄（actions，2026-07-31 新增）

**常駐 icon 鈕上限 3 顆；第 4 顆起收進 `RowActionsMenu`（`⋯`），而且收就收到只留最常用的一顆
（多半是「編輯」）在外面。**

為什麼是這兩段而不是一條線：三四顆 icon 鈕並排在手機上既擠、又**全都要靠 hover 才知道是什麼**；
而 `⋯` 自己也佔一格，「3 顆＋⋯」跟「4 顆全攤」在寬度上沒有差——要收就要收到有感。

- **條件不成立的動作整條不放進選單，不是放進去再 disable**——點不下去的項目會被當成壞掉。
  `RowActionsMenu` 自己也照這條：一項都不剩時**整顆 `⋯` 不渲染**（留一顆點開是空的鈕比沒有鈕更糟）。
- **不可用的破壞性動作沿用既有判準：選項根本不出現**，而不是給一顆按下去會失敗的鈕
  （公司管理的「刪除（僅限誤建）」2026-07-21 就是這樣定的）。
- 這條規則是**照現況訂的**，2026-07-31 盤點十個表格頁的常駐鈕數（當時只有一頁違規，已修）：

| 常駐顆數 | 頁面 |
|---|---|
| 2 顆＋`⋯` | 使用者、員工 |
| 3 顆 | 角色、組織管理、選項 |
| 1～2 顆 | 部門、群組、權限覆寫、稽核 |

> ⚠️ **這條慣例原本只寫在 `RowActionsMenu.vue` 的檔頭，沒進本書**——於是 2026-07-31 做
> 名片背景管理頁時破了它，做出全站唯一 4 顆的一頁。
> 程式註解不是規範：**連 grep 都不會想到要 grep 它**。
> （同族＝2026-07-28 那條「規則只寫在文件裡＝規則不存在」，這是它的下一層。）

### 5.5 順序（order）管理

> ⚠️ **名詞**：「排序」中文兩義——sort（升降冪）vs **order（排列序位）**。本節指後者。

- **順序是主檔自己的屬性**，在該主檔管理頁維護（Salesforce picklist／Odoo sequence 同理）；存一份、所有 consumer 讀同一份，**不要每個表單各自定義順序**。
- 三原則：①`order` 一律「**相對同層兄弟**」②UI 用**拖曳**（`OrderManager`＝握把拖＋「依名稱排序」一鍵＋**批次儲存/取消**，非邊拖邊存）③建立/編輯 modal **不放** order 數字欄，新增自動排最後。
- **數字給人看一律 1-based**（`order + 1`），0-based 只留程式內。
- 後端 reorder 端點收「排好的 id 陣列」→ 交易重編 0,1,2… ＋ audit。
- UI＝**modal**（工具列「調整順序」鈕開），清單窄單欄 `max-w-2xl`、可捲、序號 1-based 徽章。

### 5.5.1 定義列（唯讀資料的 `dl`，2026-07-24 新增）

唯讀資料頁（帳號中心個人資料等）的欄位陳列：

- **單值欄位配成兩欄**（`sm:grid-cols-2`），`sm` 以下自動回單欄。
  8 個欄位一行一個會拉出很長的卡片、右側整片留白；配對後高度直接砍半
  （實測任職資料卡 512px→269px，桌機省 47%、手機 704→448 省 36%）。
- **label 與 value 要拉開層級**：label `text-xs text-muted` 固定寬、value `text-sm text-highlighted`。
  兩者完全同樣式時，掃視會糊成一片、眼睛沒有著陸點。
  **層級只靠「字級（xs／sm）」＋「色階（muted／highlighted）」兩軸，不要再加字重。**
  > 2026-07-28 修正：本條原本寫 value 用 `font-medium`，與 §3.3／§13-11「禁 `font-medium`」直接打架。
  > 系統中文字只有 400/700，**500 的墨量比＝1.000（no-op）**——原本那個字重從來沒有生效過，
  > 拉開層級的一直是字級與色階。拿掉它是零像素變化。
- **手機維持 label／value 同一行**（不要上下堆疊），比堆疊更矮。
- **⚠️ 長值（email 等無空白字串）要不撐破版面，「列」與「value」都要 `min-w-0`，缺一不可**：
  ①列是 grid item，`min-width:auto` 使其最小尺寸＝內容 min-content，
  grid 欄會被撐到比容器還寬（實測欄 328.7px vs 容器 285px）
  ②value 是 flex item，同樣不會縮到小於內容寬。
  `break-words`（`overflow-wrap:break-word`）**只在排版時允許斷字、不會縮小 min-content**，單靠它救不了。

> **⚠️ 這類溢出用 `scrollWidth > clientWidth` 驗不出來**——元素會自己撐大，兩者永遠相等。
> 正確驗法＝比對「**右緣是否超出容器內容框**」。2026-07-24 因此誤報過一次「沒有溢出」，
> 實機才被 Steven 抓到被切掉。附帶：該 email 在 375px 下恰好 197px、可用寬也恰好 197px，
> **零餘裕**——這種「剛好塞得下」在不同裝置的字體渲染下必然翻車，量到剛好就要當成不合格。

> **⚠️ 多值欄位一律跨整列（`sm:col-span-2`），不參與兩欄配對。**
> 多值＝角色、標籤、分眾這類「數量不固定的徽章清單」（§5.4 已把它列為不給排序的欄型，同一個分類）。
> 理由不只是自己會擠：**CSS grid 同列等高，多值欄一膨脹會把隔壁的單值欄一起撐高**，
> 下方留一大片空白。實測 6 個角色在半欄折成 3 行、把隔壁「公司信箱」撐到 109px；
> 跨整列後 6 個角色一行放得下、列高 49px，**整個區塊反而更矮**。
> 一個帳號可跨模組掛多個角色（`UserRole` 多對多、`Role` 各綁一個模組），這不是極端情境。
> CRM 的客戶標籤／分眾是同一個形狀且數量更多，比照辦理。

> **⚠️ 分隔線只畫在「列與列之間」，最後一列不畫（2026-07-31 修）。**
> 定義列幾乎都被放進帶框容器（公司資訊框、帳號中心的區塊）。最後一列若也畫下框線，
> 它會與**外框的下緣緊貼**——實測兩者間距 `0.00px`，兩條 1px 疊成視覺上一條 2px 的粗線。
> **後面還接東西的使用點（說明段等），分隔線由那個東西自己帶 `border-t`**：
> 誰要被分隔誰負責，元件的下緣就不必看它被放在哪。
> ⚠️ **實作雷**：兩欄版的「最後一列」可能是**左右兩格**，左邊那格不是 DOM 的最後一個，
> `last:` 抓不到；但 `<sm` 是單欄，那時反而只有 `last:` 是對的。
> 正解＝算出每格的視覺列索引 → 旗標只在 `sm:` 生效、`last:border-b-0` 常駐。
> **同族的通則：任何「容器有框 ＋ 內容最後一項也有框」的組合都要檢查這件事**
> （清單、手風琴、divide-y 的區塊）——它不會報錯，只會讓下緣看起來比別處粗一點點。

### 5.6 容器範式：modal／整頁／drawer（2026-07-23 新增）

> §1 原則 1 只寫「建立/編輯開 modal」，**沒有上限**。本節補上邊界。
> 起因：CRM 的客戶詳情會長成「基本資料＋聯繫紀錄＋消費總表＋標籤＋諮詢 case」，
> 照字面套 §1 會做出一個塞不下的 modal。
>
> ⚠️ **本節是初版，尚未經實際使用驗證**（2026-07-23 訂）。用到覺得不對就回來改，
> 改的時候把「哪個頁面、為什麼不適用」一起寫進來。

**判準不是「資料多少」，是這三問，由上往下問：**

| # | 問題 | 是 → | 否 → |
|---|---|---|---|
| ① | 這東西需要**有自己的網址**嗎？（貼連結給同事、重新整理後還在、瀏覽器上一頁要有意義）| **整頁** | 往下 |
| ② | 使用者需要**一邊看它、一邊參照背後的清單**嗎？ | **drawer / slideover** | 往下 |
| ③ | 做完之後是**回到原地繼續**嗎？ | **modal** | 整頁 |

**第①問是最硬的判準**——能不能分享、能不能加書籤、瀏覽器上一頁會不會壞掉，
這三件事 modal 永遠給不了。有疑慮時先問這一題。

**一條硬上限（凌駕上表）**：欄位超過約 8 個、或需要 tabs 才裝得下 → **一律整頁**。
塞不下的 modal 會逼使用者在小視窗裡捲動填表，是最差的體驗。

## 6. 元件規範

### 6.1 按鈕階層

| 用途 | 寫法 |
|---|---|
| 頁面主要動作 | `color="primary" variant="solid"` |
| 次要動作 | `color="neutral" variant="outline"` |
| 工具列／utility | `color="neutral" variant="ghost"` |
| 需要灰色填滿感 | `color="neutral" variant="soft"` |
| 有風險但非破壞性 | `color="warning" variant="soft"` |
| 破壞性 | `color="error" variant="soft"` 或 `outline` |

> ⚠️ `neutral + solid` 會近黑，**不要拿來當一般灰按鈕**。

**icon-only 鈕三問**（藏字之後必問，一天踩兩次的教訓）：

1. **padding 等距了嗎？** 文字藏了但仍留文字鈕的左右 padding → 變橫長方形。md 尺寸鈕補 `max-sm:p-2.5`（36×36，同全站 square md 規格）。
2. **置中了嗎？** 固定尺寸（如 `max-md:size-10`）必須同時 `:ui="{ base: 'justify-center p-0' }"`——UButton 預設非置中。
3. **`aria-label` 還在嗎？** 藏字用 `max-sm:hidden` ＋ 保留 `aria-label`/`title` 全文；**不要**用 `max-md:size-10` 硬縮還留著文字。

### 6.2 表單輸入

| 規則 | 值 | 原因 |
|---|---|---|
| 輸入框字級 | **手機（<640px）16px、桌面 14px** | iOS 點擊 <16px 的輸入框會整頁放大 |
| placeholder | 手機縮為 `text-sm` 顯示 | iOS 縮放只看輸入文字字級，placeholder 可獨立縮小 |
| 欄位標籤/說明/錯誤 | **固定 14px，不隨 input size 放大** | 16px 底線只限輸入控件；formField theme 已鎖回 |
| 16px 底線範圍 | **只限輸入控件**（input/select/textarea） | 表格、標籤、說明等顯示文字不受限 |
| 無標籤欄位 | 必須有欄位外說明文字撐住語意 | 標籤與 placeholder 不可同時缺席 |

- **說明/備註欄**：獨占一列 → `<UTextarea :rows="3" class="w-full" />`；跟單行欄位同排 grid → 維持 `AppInput`（textarea 高度突兀）。
- **必填星號只有「同表單有可選欄位可對比」時才標**。整張表單每欄都必填就不要標（整排星號傳達不了資訊）。**標了就要在 schema 裡真的驗。**
- **placeholder 要舉例，不要複述欄位名**：「科威員編」配「例如：Y001」，不是「請輸入科威員編」。（密碼類無法舉例，屬例外。）

#### 6.2.1 必填／選填怎麼講（2026-07-31 定案）

**分界＝這個欄位有沒有標題。** 有標題的靠紅星對比，沒標題的星號無處可放，只能用文字。

| 欄位形狀 | 必填怎麼講 | 選填怎麼講 |
|---|---|---|
| **有標籤**（`UFormField`） | 紅星（上一條的規則） | **什麼都不寫**——沒有星號本身就是答案 |
| **無標籤的可增刪列表**（一列多格，如聯絡方式、樓層資訊） | **區塊標題下方一行說明**（`text-xs text-toned`，§2.5.1） | placeholder 尾綴 `（選填）` |

- **「（選填）」不准出現在有標籤的欄位**——同表單已經有紅星可對比時再寫一次是重複。
  2026-07-31 一輪清掉 8 處（3 處在 label、5 處在 placeholder）。
- **必填一律不寫進 placeholder**，兩個理由缺一不可：①塞不下（「樓層名稱（必填），例如：9樓」
  放不進 `sm:w-40`）；②**跨欄位規則本來就不是單格講得完的**——「電話與傳真至少填一個」
  要寫進哪一格？寫兩格是重複、寫一格是騙人。
- ⚠️ **這條的觸發點是「盤點選填時發現必填根本沒標」**：公司表單兩個可增刪列表裡，
  `樓層名稱`／`聯絡用途`／`電話傳真擇一` 三條必填規則**畫面上一個標示都沒有**，
  標出來的全是選填的那幾格，而規則只在按下儲存時由錯誤訊息講。
  **判準：一整列欄位都沒有標題時，先問「哪幾格非填不可，使用者從畫面看得出來嗎」。**

### 6.3 狀態徽章的顏色語義

| 顏色 | 語義 | 用在 |
|---|---|---|
| `success` | 正常運作中 | 啟用、在職 |
| `warning` | **待處理——有人要去追** | 邀請中（還沒設密碼）、留職停薪 |
| `neutral` | 非啟用，但一切正常 | 停用、離職 |
| `error` | **真正的錯誤或破壞性結果** | 匯入失敗、驗證不通過 |

**關鍵判準：`error`（紅）不是「負面」，是「出事了」。**
員工離職導致帳號停用是系統照設計正確運作，標紅會把視線拉到一件完全正常的事上；紅色被這樣用久了，真的出事時就沒人看見。

**這組對照必須有單一來源**＝`apps/portal/src/shared/lib/account-status.ts`，新頁面一律從那裡取（含稽核詳情的前後對照，否則同一件事在列表寫「停用」、稽核寫「已停用」像兩件事）。

### 6.4 Tooltip

**一律 `UTooltip`**，唯一例外＝**輸入框內緣的小圖示鈕**（見 §8.1-4）——浮層會蓋住 26px 的小鈕，滑鼠移過去先開浮層就點不到。例外處要**在原地寫下理由**，否則下一輪巡檢又會有人「順手統一」改回去。

官方主題把 tooltip 的 `text` 設成 `truncate`（**提示被截斷等於沒有用**），全域改掉：

```ts
tooltip: {
  slots: {
    content: 'rounded-xs h-auto max-w-xs whitespace-normal',
    text: 'whitespace-normal',
  },
}
```

`h-auto` 不能漏——原主題有固定高度，只放開 `whitespace` 第二行會被切掉。

### 6.5 Icon

- **一律 lucide（`i-lucide-*`），禁止混用其他 icon 套件**——不同套件筆觸/比例不一致，混排一眼突兀。
- lucide 找不到想要的先上 lucide.dev 搜（新 icon 常已收錄），真沒有再帶候選來討論，**不要自行混套件**。
- 裝飾用 emoji 一律換成 lucide icon。
- ⚠️ icon 目前執行期從 Iconify API 抓（斷網會開天窗），內網正式部署前要把 lucide collection 打包進本地。

#### 6.5.1 尺寸：照**結構角色**訂，不照「看起來大不大」（2026-07-28）

判準是「這顆 icon 服務的對象是誰」，不是它旁邊的字幾號、也不是主觀的輕重感。
（軸選錯的症狀：訂完馬上要為某個畫面開例外——見 §2.5.1 同一條教訓。）

| 角色 | 尺寸 | 實例 |
|---|---|---|
| 與**單行**文字並排（屬於那一行） | `size-4`（16px） | breadcrumb／導覽項前導、列內 meta、狀態列的成功/失敗記號 |
| 服務**多行區塊**（標題＋說明），或**獨立存在** | `size-5`（20px） | 設定列（`AccountAppearancePage`）、`DismissibleBanner`、`ModuleRail`、空狀態、載入 spinner |
| **整頁的狀態主角** | `size-6`（24px） | 回呼頁的成功／失敗／loading |
| 空白區的放置圖 | `size-7`+（28px+） | 頭像上傳的拖放區 |

**明文例外——toast 用 `size-4`（Steven 2026-07-28 拍板）：**
它結構上屬於「多行區塊」該用 20px，但 toast 是寬約 380px 的**緊湊浮層**，
而設定列是頁面內的寬列——**同一個 px 在兩者的感知重量不同**。三種尺寸並排實物比較後選 16px。
這是刻意的例外，不是漏改；規則其餘部分不受影響。

> ⚠️ **改 icon 尺寸時，要看那一排上所有同高的東西，並確認「對齊」不是巧合。**
> toast 原本 icon 20px **剛好等於標題行高 20px**，中線自然吻合——那是巧合。
> 縮到 16px 後前導 icon 與關閉鈕**同時**偏高 `(20−16)/2 = 2px`，兩顆都得補 `mt-0.5`
> （root 是 `items-start`，這是對的：多行時 icon 要對齊**第一行**而不是整塊中線）。
> 這類偏移不會有任何東西報錯，只能靠量（比對 icon 與標題的**中線**）或靠眼睛。

### 6.6 頭像與圓形裁切

**任何 `rounded-full` + `overflow-hidden` 的容器都必須有背景色；有 `ring` 時背景色要與 ring 同色。**

圓形裁切邊緣是反鋸齒的，那圈半透明像素必須跟底下的東西混色；容器沒背景色就混到後面的內容（頭像跨在深色背景照與白卡交界時，只有上半圓看得見細邊）。

**結論：頭像一律用 `UAvatar`**（根元素本來就帶 `bg-elevated`），不要手刻 `<img class="rounded-full">`。

### 6.7 空狀態與其他

- **`EmptyState`**：`UEmpty variant="naked"` ＋ `border-dashed`（官方 outline/subtle 的框是 `ring`＝box-shadow，做不出虛線）。`sm`＝窄欄用、`md`＝大區塊。
- **浮層裡的空狀態（可搜尋下拉、command palette…）＝借 `EmptyState` 的結構語言，但不要套那個元件。** 它是虛線框＋24px 內距，塞進浮層會變成「框裡面又一個框」（同樹狀選項踩過的兩層框）。
  做法：小 icon（`size-5 text-dimmed`）／標題 `text-default`／說明 `text-xs text-dimmed`，**層次靠顏色做**——官方 `empty` 插槽外層已經是 `text-sm text-muted` 置中，標題不升 `text-default` 的話兩行會糊成一坨（2026-07-23 實作時 Steven 當場退回過一次）。
- **選項範圍有收斂時，空狀態要「指路」，不能只說「找不到」。** 清單本身有範圍限制（例：稽核的動作下拉跟著檢視分頁收斂）時，攤開清單使用者看得到範圍、不會誤會；**一旦加了搜尋框，空白就讀起來像「系統沒有這個東西」而不是「你在錯的地方」**。
  要接著講出正確的位置（「切到『登入與安全』分頁再搜尋看看」），且**位置名從資料反查、不要寫死文案**——之後新增選項或分頁才不必回頭改字。
- **空值一律 `—`（em dash）**：`?? '—'` 或 `<span class="text-dimmed">—</span>`，不准出現 `-`／`_`。
  - ⚠️ **例外：「沒有值」本身是一個有名字、需要有人處理的狀態時，寫那個名字，不要寫 `—`**
    （2026-07-28 部門主管懸缺）。判準是**看有沒有人要為這個空負責**：
    「還沒填備註」沒有人要負責 → `—`；「這個部門現在沒有主管」有人要去補 → 「懸缺」。
    寫 `—` 會讓使用者以為是資料沒帶到、系統壞了，而不是「這裡缺一個人」。
  - 色階仍照空值處理（`text-muted`／`text-dimmed`），**不要用 warning 徽章**——
    這種狀態常常是多筆同時發生（部門主管初始全空），整欄警示色會變成雜訊而不是提示。
    真正該叫人的是通知，不是顏色。
  - ⚠️ **日期欄不要自己寫空值**：`shared/lib/datetime.ts` 的格式化函式已經在值為空／格式壞掉時
    回傳 `EMPTY`，那個常數就是唯一出口。**巡檢時要看的是那個常數，不是各頁。**
    2026-07-31 之前它是半形 `-`，於是**全站每個日期欄都跟旁邊的文字欄長不一樣**
    ——業務頁手寫的 29 處一直都是對的，錯的只有這一個字（Steven 從「最後登入」欄看出來）。
  - ⚠️ **不要寫「規範沒定所以維持現況」的測試**：上面那個 bug 掛了兩天沒被修，
    是因為有一條測試斷言 `toBe('-')`，註解寫著「design.md 目前沒有定這件事」
    ——**而規則就在本節與擋件第 7 條**。任何人把它改對都會看到紅燈，
    **紅燈會讓他以為現況才是對的**。這比沒有測試更糟：它把違規包裝成「已知的刻意現況」。
    **寫「規範沒定」之前先去查規範**；真的沒定就當場定，不要用測試把現況焊死。
- **顯示給使用者的資料用中文名，不露 code**：有 code＋name 的實體一律顯示 name（hover 補英文代碼）。
- **modal 縮窄**：欄位少的建立/編輯 modal 用 `width-class="sm:max-w-md"`，別用預設 512 太寬。
- **有輸入欄位的 modal 一律走 `FormModal`，不要手刻 `UModal`**（2026-07-23 收斂帳號中心三顆）。
  手刻的會少掉晃動提示、footer 樣式與標題凍結，行為跟其他頁不一致。
- **點遮罩能不能關＝看「誤關的代價」，不是看畫面大小**：
  - **鎖住（預設，`dismissible=false`）**：有打字的表單。誤關要重打，代價高 → 點遮罩改成
    **晃一下**（macOS 對話框手勢），明確告訴使用者「這裡關不掉，走取消或 X」。
  - **可關（`dismissible`）**：挑一下就走的輕操作（換頭像、選名片背景）。誤關重開零成本，
    鎖住反而礙事。
  ⚠️ **「有擋但沒有回饋」＝使用者會以為程式壞了**——這正是手刻 UModal 的問題（點遮罩靜默無反應）。
  要嘛給晃動，要嘛就讓它關。

## 8. 互動與狀態規則

### 8.1 控件狀態五條硬規則

1. **停用的控件不准對滑鼠有任何回應**：`hover`/`active` 一律掛 `not-disabled:`。停用還會變邊框，使用者會以為點得動。（已在 `vite.config` 的 button/input/textarea/select/selectMenu theme 補齊。）
   ⚠️ **只要你覆寫了 hover 的底色或邊框，就要自己補 gate——官方的 `disabled:` 保護不到你的覆寫。**
   官方 theme 用 `disabled:bg-*` 把停用態壓回去，那只蓋得住官方自己的 hover 值；我們在同層寫的
   `hover:bg-*`／`aurora:hover:bg-*` 特異性相同、順序在後，照樣贏。
   **踩法（2026-07-23）**：light 看起來正常、dark/aurora 才露餡——因為 light 我們的 hover 值恰好
   與底色同值（巧合，不是設計），aurora 換成半透明值就現形。
   **檢查法**：`vite.config` 裡搜 `hover:`／`active:`，每一條問「這是我們自己寫的嗎」，是就要有 `not-disabled:`；
   驗證要**真滑鼠 hover ＋量 computed**（停用件 hover 前後同值），別只看截圖。
   **另外**：這條講「停用不准有**反應**」，第 5 條講「停用要看得出來」——兩條是一體兩面，一起讀。
2. **警告色只留給「真正需要行動」的事**：狀態資訊用欄位＋篩選呈現，不要常駐警告。天天顯示不是問題的事，只會訓練使用者無視所有警告。
3. **連動下拉：父層沒選就 disabled，並用 placeholder 講下一步**（「請先選擇公司」）。**同一條規則要同時套到 modal 表單與篩選列**，且父層變更/清空時一併重置子層。
4. **輸入框內緣的小圖示鈕用原生 `title` 不用 `UTooltip`**（見 §6.4），並**一律加 `@mousedown.prevent`**——不擋的話按下瞬間輸入框先失焦，表單會用舊值跑驗證而閃出錯誤。
5. **停用態要看得出來，而且每一種變體都要各自處理**（2026-07-28 補）。
   規則一句話：**停用＝降級成「中性版本」＋ 文字掉到最弱階**——
   文字與圖示 `text-dimmed`（icon 走 `currentColor` 會一起變）、`outline`／`subtle` 的邊框
   `ring-accented`、`soft`／`subtle` 的底 `bg-elevated`、`solid` 另外壓中性底。
   ⚠️ **`base` slot 的樣式是全變體通用的。** 你為了做 solid 的停用底而在 `base` 寫
   `disabled:opacity-100`，等於**同時解除了 ghost／outline／link／soft／subtle 的官方
   `disabled:opacity-75`**；若補回來的中性色只掛在 `variant: 'solid'`，那五種變體停用後
   **一個像素都不會變**。
   **踩法（2026-07-28，ystravel-platform）**：改完 solid 停用色的當天下午，才在群組管理頁發現
   停用的 icon 鈕與可按的**逐位元同色**（`oklch(0.92 0.004 286.32)`），刪除鈕甚至還是全飽和的紅。
   全站 16 處（ghost 7／outline 6／link 3）一起中招。**手機更糟**：沒有 hover 就沒有 tooltip，
   那句「為什麼不能按」的 `title` 永遠不會出現——使用者點下去毫無反應也毫無解釋。
   **為什麼是 `dimmed` 不是 `muted`**：`link` 變體可按時就已經是 `text-muted`
   （官方 neutral link ＝ `text-muted hover:text-default`），停用再給 `muted` 等於沒改；
   一條規則要涵蓋所有低強度變體就只能落在再下一階。`dimmed` 對白底 2.60 未達 AA 是**刻意**的——
   WCAG 1.4.3 明文豁免停用控件，Material 3 的停用文字（on-surface 38%）算出來也在 2.4 上下；
   §2.5「dimmed 不得承載必要資訊」講的是**還要讀**的資訊，停用鈕要傳達的就是「現在不能按」。
   **為什麼不乾脆把 `opacity` 加回來**：單一透明度會連中文字一起弄糊
   （Material 刻意把底 12%／字 38% 分開就是為此）。
   **檢查法**：光看對比比會漏——紅→灰的對比比只有 1.23（對比比只量亮度），畫面上卻是天差地別。
   要量就量 **OKLab ΔE**（含彩度），且 **variant × color × 主題（light／dark／aurora）每格都要量**。
   實測收斂在 ΔE 0.15～0.50，最弱的是 `link/neutral`（0.154～0.159，因為它起點就已經是 muted）。

### 8.1.1 載入狀態（2026-07-27 定案）

**共用元件＝`shared/ui/feedback/LoadingState.vue`**（原 `TableLoading`，2026-07-27 改名——
它從來不限表格用，但名字讓每個人以為表格以外要自己刻，於是長出五種寫法：
純文字「載入中…」、純文字「載入中⋯」（連刪節號都不同字元）、手刻 spinner ＋自訂文案、
只有 spinner 沒文字、以及共用元件本身）。

**選哪一種：**

| 情況 | 用什麼 | 為什麼 |
|---|---|---|
| **知道內容的形狀**（定義列、卡片、固定幾行的區塊） | `USkeleton` 排成那個形狀 | 載入完不會跳版；使用者提早知道會出現什麼 |
| **不知道形狀**（表格、清單、整頁、未知筆數） | `LoadingState`（spinner ＋「載入中」） | 骨架屏猜錯筆數反而更晃 |

**硬規則：**

1. **不准只給純文字。** 靜止的「載入中…」跟當掉的畫面長得一模一樣；spinner 的唯一功能就是
   證明「還活著」。
2. **不准只給 spinner 不給文字**——轉圈不會告訴人在等什麼；`LoadingState` 的 `label` 有預設值，
   要客製才傳（例：「讀取角色權限中」）。
3. **文案一律「載入中」，不加刪節號。** 動畫已經表達了「進行中」，`…`／`⋯` 只是多一個會寫錯的字元。
4. **空狀態一定要排除 loading**：`v-if="loading"` 要排在 `v-else-if="empty"` 之前，
   否則資料還沒回來就先閃一下「沒有資料」或「你沒有權限」的假訊息（Steven 2026-07-20 回報過）。
5. ⚠️ **驗證載入動畫時，瀏覽器窗格必須是顯示狀態**——隱藏的窗格會凍結動畫時間軸，
   量到的是動畫起始值（見 `operations/TROUBLESHOOTING.md` 的「隱藏頁面動畫不可信」）。
6. **骨架要排的「那個形狀」包含外殼——骨架不准直接鋪在頁面底上**（2026-07-28 補）。
   `USkeleton` 官方底色是 `bg-elevated`，而 **light 的 `bg-elevated` 與 `--app-surface-page`
   逐位元同色**（實測分離度 **1.000**）。骨架在 DOM 裡、也在動，就是看不見。
   **踩法**：管理中心「通知」頁原本是兩塊裸的 `USkeleton h-40` 直接放在頁面上，
   **淺色模式整頁空白**；深色看得到純粹是因為 dark 的 `bg-elevated` 被推到 `neutral-700`
   （§2.4 那次為了解決卡片撞色做的，順便救了這裡——所以這個洞只會在淺色露出來）。
   **正解**：外殼用真的卡片元件（卡片底本來就與頁面分層），骨架只畫裡面的行。
   順帶把兩塊沒有內容的灰方塊變成真的預覽——**灰方塊沒有告訴使用者等一下會出現什麼**，
   那不算「排成那個形狀」。
   **驗收**：骨架卡高度要等於真實卡片高度（該頁實測兩者都是 166px，載入完成零跳版）。
7. **骨架的灰階明暗各自訂，不要共用一個 token**（2026-07-28 補）。
   `bg-elevated` 在明暗兩邊的分離度差很多：dark ＝ `neutral-700` on 卡片 → **1.428**，
   light ＝ `neutral-100` on 白卡 → **1.101**，比本節 §8.1 定義的「hover 本來就該微妙」
   （1.086）還接近。而 `animate-pulse` 谷底會掉到 50% 透明，現況等於有半個週期幾乎看不見。
   **骨架條是內容的預留位，不是微妙回饋。**
   > **拍板值＝ light `neutral-200`（1.238）／dark `neutral-700`**（Steven 2026-07-28
   > 三階並排看過後選的）。**刻意沒取數值上與 dark 對齊的 `neutral-300`（1.472）**——
   > 那階在白卡上偏重。**明暗不追求同一個數字，追求各自看起來對**，這點與 §2.7
   > 「好看優先」的例外同一個判準。

### 8.2 Dark mode 與浮層

- **dark 下不靠 `shadow` 製造浮起感**（陰影幾乎看不見），改用 **`ring-1 dark:ring-white/25` hairline ＋ 深色明度分層**。
  **色階一律以 §2.4 的 `--app-surface-*` 表為準**：頁底 `neutral-950`（最深）< 卡／modal／殼件 **`800`** < 卡內區塊 `900`；
  井底層（輸入框／`TableFrame`／`OrderManager`）維持 `950`、斑馬偶列 `900`。
  已抽到 `vite.config` 各 content slot，新元件自動套用。
  > ⚠️ **2026-07-28 修正**：本條原本寫「卡／modal／側欄 `850`」——那是 2026-07-24
  > 「表面層級收成 token」**之前**的值。改版後卡片是 `800`，而 **`850` 只剩表格深色標題帶在用**
  > （§2.4 明訂那不是表面層，是刻意的深色標題帶）。
  > 照舊值寫 `neutral-850` 當卡片底**不會報錯**，只會讓卡片對頁面的分離度悄悄少一階
  > ——**同一份規範裡有兩個互相矛盾的數字，比沒寫還危險**。
- **浮層一律 `bg-[var(--app-surface-card)]` ＋ `dark:ring-white/25`——`toast` 也是浮層**（2026-07-28 補）。
  官方 toast 的 root 是 `bg-default shadow-lg`：dark 解析成 `neutral-900`，只比頁底亮一階，
  而陰影在深色又看不見，於是整個 toast 幾乎融進背景。
  **改底色時 dark 的 ring 要一起換**——官方 `ring-default` 在 dark ＝ `neutral-800`，
  與新底色同色，框線會直接消失、浮起感反而更差。
  > toast 是**最後一個**沒被收進表面系統的元件（其餘 13 個在 `vite.config` 都覆寫過了），
  > 一直到有人在畫面上看出來才發現。**新增一類元件時要先問「它是不是浮層」**，
  > 而不是等它在深色下出事。
- **【鐵律】dark 裝飾效果不准動到 light**：裝飾層用 `hidden dark:block` 只在 dark 掛載；效果 class 一律 `dark:` 前綴。**改完務必切 light 實測 computed** 才算數。
- **遮罩（scrim）全站同一種深度＝`bg-black/50 dark:bg-black/70`**（2026-07-23 定）。官方預設是
  `bg-elevated/75` 霧白，深色頁面上分離感不足；dark 加深到 70% 對齊 Material dark 慣例（60~70%）。
  ⚠️ **三個元件的層位不同，覆寫要各放各的同層才贏**：`modal` 的底色在 **overlay 變體層**
  （`variants.overlay.true.overlay`）、`drawer`／`slideover` 在 **slots 層**（`slots.overlay`）。
  放錯層＝靜默無效。改遮罩時**三個一起改**，別只改 modal（drawer/slideover 曾漏改半年）。

### 8.3 錯誤顯示三層

> 原則：**能預防就不報錯；報錯盡量貼著欄位；toast 是最後手段**。

1. **預防層（UI 直接擋）**：日曆反灰不可選日期、下拉只列合法值、按鈕 disabled。
2. **前端驗證層 → 欄位下方紅字**：走 `FormModal` 的 `:schema`（valibot）→ UForm 行內驗證。schema 管不到的欄外狀態自寫即時計算函式，紅字（`text-xs text-error`）放欄位正下方＋submit 入口再擋一次。
   - **紅字左緣對齊 input 起點，不是容器左緣**：label 在左的行內佈局用 `col-start-N` 對到 input 那欄——錯誤講的是「這個欄位」；靠容器左緣會像整張卡在報錯。
   - **瀏覽器原生驗證氣泡全站禁用**（`FormModal` 的 UForm 已掛 `novalidate`）：位置不可控、各瀏覽器長相不一，且它搶在 schema 驗證前跑＝行內驗證永遠沒機會顯示。新表單不准依賴原生 `required`/`min`/`pattern`。
3. **後端錯誤層**：
   - **對得到欄位的**（email 已存在、名稱重複）→ 盡量映射回該欄位下方紅字；映射不了才 toast。
   - **對不到欄位的**（500／網路／權限／整批失敗）→ toast（error 色＋`i-lucide-circle-alert`），文案走各 api 層的 `ERROR_MESSAGES` 中文對照表。

### 8.4 RWD 補充

- **分頁 footer**：`<sm` 2 欄 grid（分頁置中橫跨上排、下排「共N筆」左＋「每頁」右）；`≥sm` 一列 `justify-between`。
- **`DataToolbar` inline 模式**：動作少的頁小螢幕也單列（搜尋 `flex-1`＋動作貼右）；動作多維持堆疊。

### 8.5 捲動與畫面角落的浮動元件（2026-07-23）

**捲的不是 window。** `AppShell` 是 `fixed inset-0 overflow-hidden`，真正在捲的是 Nuxt UI
dashboard panel 的 body——`window.scrollTo` / `window.scrollY` / `useWindowVirtualizer`
在本站**通通沒作用**。任何跟捲動打交道的功能一律用共用的
`shared/composables/useScrollRoot`，不要自己寫一份（那個判定有 CSS 陷阱，見
`operations/TROUBLESHOOTING.md`）。

**長清單一律跟著整頁捲，不要給它自己的捲動區。** 「頁面主體就是一張表／一棵樹」的管理頁，
標準做法是整頁捲＋底層虛擬化。硬塞一個 `max-h` 內捲區塊會同時製造兩個問題：桌機高螢幕
下方留一片空白、手機變成頁面與清單**兩層巢狀捲動**（2026-07-23 選項樹踩過，Steven 回報）。

**畫面角落只能有一個常駐主角。** 右下角歸**全站回頂部鈕**（`i-lucide-arrow-up-to-line`、
圓角正方、桌機 40×40／手機 36×36、`fixed right-4 bottom-4 z-40`）：

- 捲超過 **400px** 才淡入；**捲到頂整顆移除**（`v-if`，不是變透明）——不佔位就不可能擋到手機內容
- 桌機 toast 也在右下 → **toast 讓位**：viewport 從 `bottom-4` 抬到 `bottom-20`，
  **只在按鈕顯示時抬**（固定抬高會讓頁面頂端的 toast 下方空一段沒有理由的距離），
  並加 `transition-[bottom]`——沒有它，顯示中的 toast 剛好跨越門檻會「跳」一下，讀起來像 bug
- ⚠️ **不要把 toast 改到 `top-right` 來閃避**：實測會蓋住 header 的「內部收件匣」鈴鐺，
  疊 4 則時整個右上被吃掉；通知 toast 蓋住通知鈴鐺說不過去
- 手機 toast 在 `top-center`，與按鈕不同角落，不需處理

**長清單的效能門檻。** 每列的成本要算**元件實例**而不是 DOM 或按鈕數——包裝元件比被包的那顆
還貴（選項樹實測每列 64 個實例，其中約一半來自 5 個 `UTooltip` 的四層包裝）。
可見列數可能破百的清單一律虛擬化（`@tanstack/vue-virtual`，flatten visible nodes + windowing），
不要靠「加個 loading 遮一下」掩飾卡頓。

## 9. 主題系統（深淺色 ×主題）

**架構**：深淺色「模式」之下各自可選「主題」。深色＝**極光（預設）／預設（純黑）**；淺色＝預設 only。存 localStorage（`ystravel.platform.theme.dark/light`，每台裝置各記；色彩模式另存 `ystravel.platform.color-mode`）。

**外觀模式有三個值：淺色／深色／跟隨裝置，預設＝跟隨裝置**（2026-08-05）。判準沿用 §3.4 決定字級歸屬那條——**這個偏好描述的是「環境」還是「身體」**：主題是環境（辦公室日光燈 vs 家裡關燈），既然是環境就跟著裝置走；字級是身體，所以不跟。

⚠️ **`auto` 只存在於「使用者選了什麼」那一層，永遠不會變成 html 的 class**——套上去的一律是解析後的 `light`/`dark`。控制項要顯示的值必須讀「他選的」那一個；讀「現在是不是深色」的話，選了跟隨裝置之後控制項會自己跳到 light 或 dark，看起來像他選了固定模式。

⚠️ **改這類「有預設值又存 localStorage」的偏好時，先問舊值是不是歧義的。** 2026-08-05 這次：舊預設寫死 `light`，而 VueUse 的 `useStorage` 預設 `writeDefaults: true`——**使用者沒選過，`light` 就已經被寫進去了**，於是存著的值分不出「他選的」和「系統寫的」。只改預設對已經用過的人完全無效，必須連舊值一起清。**上線前清幾乎零成本，上線後就只能在「不動使用者設定」和「功能有意義」之間二選一。**

⚠️ **公開頁（不需登入的那幾頁）一律淺色，不跟隨裝置**（2026-08-13 Steven 發現後拍板）。
目前是登入／忘記密碼／設定密碼／Google 回呼四頁——它們的視覺是**寫死的淺色設計**
（實測 `dark:` 出現次數是 **0**），所以整頁強制 `light`。

**為什麼不是「只把 toast 改成淺色」**：toast 由 `UApp` 在**根層級**渲染、不在頁面裡面，
吃的是 `<html>` 上的 `.dark`——深色裝置下會出現「白底頁面 ＋ 黑底 toast」。
而 `dark:` 變體是 `:where(.dark, .dark *)`，只要 `.dark` 掛在 `<html>`，**整棵樹都符合**，
沒有辦法用 class 讓某個子樹「退出深色」。逐個元件壓的話，**下次公開頁長出
modal／tooltip／popover 會再中一次，而那時沒有人會記得有這條規則**。

**判準＝有沒有 `requiresAuth`，不另外維護路徑清單**——新增公開頁不必做任何事就自動生效；
多一份清單就多一個「新增時沒有人記得回來加」的洞。

📌 兩個實作上的關鍵（`color-mode.ts`）：
① 走 VueUse `useColorMode` 的 **`onChanged` 攔截點**改，**不要自己另外加 watcher**
——它內部是 `watch(state, …, { flush: 'post' })`，自己再加一個同 flush 的，誰先誰後
就只剩「建立順序」在決定，沒有東西守得住。
② `onChanged` **只在色彩模式變動時觸發**，所以還要一個 watch 盯著「是不是公開頁」
——否則「從深色的內頁走到登入頁」不會有任何事情發生。
📌 這只影響**套到 DOM 上的值**，不改寫使用者存的偏好（設定頁的控制項不會跳掉）。

實作＝`useAppTheme.ts`（watch 掛 html `.theme-aurora` class）＋ `main.css` 的
`@custom-variant aurora (&:where(.dark.theme-aurora, .dark.theme-aurora *))`。

### 9.1 兩條鐵律

1. **保證深色「預設」像素級等同原設計、淺色不變**：元件**只「加」`aurora:` 前綴樣式、絕不改 base class**。未來要加新主題＝新 class＋新 `@custom-variant`，同法炮製——**別回頭硬寫某個 shell**。
2. **別用 `dark:` 做「只有某主題才要」的裝飾**：`dark:` ＝ 所有深色（含純黑）都套，會破壞上面的保證。極光專屬效果一律 `aurora:`。

### 9.2 aurora 色值＝單一 token 區塊

所有毛玻璃/半透明值集中在 `main.css` 的 `.dark.theme-aurora` 區塊，元件一律 `aurora:bg-[var(--aurora-panel)]` 引用，**不准散寫 `neutral-900/38`、`white/8` 這類數字**。

| 群組 | token |
|---|---|
| 表面 | `--aurora-panel` `rail` `overlay` `field` `inset` `header` |
| 狀態 | `--aurora-row-alt` `hover` `hover-soft` `active` |
| 邊框 | `--aurora-border` `border-soft` `divider` |

### 9.3 外殼元件

- **`SurfaceCard`**＝毛玻璃卡片外殼（圓角/邊框/底/陰影＋aurora 玻璃）；`as` 控 section/div、`rounded` prop。
- **`TableFrame`**＝表格內縮帶框＋斑馬紋＋列 hover＋`#footer` slot。`TableCard` = `SurfaceCard` + `TableFrame` + 分頁。
- **`AuroraBackdrop`**＝全視窗星空＋極光光暈固定背景層，**掛在 `App.vue` 根組件**（放 `AppShell` 會每次換頁重掛載、動畫歸零）。

**維護心法**：改 aurora 顏色 → 只動 `main.css` token 區塊；新卡片/表格 → 用 `SurfaceCard`/`TableFrame`/`TableCard`，別貼長字串。

### 9.2 極光下的文字對比（2026-07-24 逐像素掃描後定案）

**極光下文字階整體提亮半階**，規則收在 `main.css` 的 `.dark.theme-aurora`：

```css
--ui-text-muted:  oklch(0.788 0.0105 286.18);  /* zinc 350 半階（原 400）*/
--ui-text-dimmed: oklch(0.6285 0.0155 286);    /* zinc 450 半階（原 500）*/
```

> **⚠️ 是半階不是整階，這點踩過坑。** 第一版提整階（muted → 300），但 **`toned` 本來就是 300**——
> 兩階變同色，五階層次被壓成四階（Steven 一看畫面就發現「沒有層次」，量測證實
> `toned→muted` 的亮度差是 **0**）。改取中點後相鄰階亮度差回到 0.222／0.117／0.172／0.240 的均勻節奏。
>
> **這兩個中點值刻意不照 §2.7 規則 6 的「最淺過標點」推導**——那條規則是為了讓組合過 AA，
> 而這裡的目的是**層次間距**，且極光下本來就過不了。取中點才能讓五階等距。

**不要再逐處貼 `aurora:text-muted`／`aurora:text-toned`**（§13-31 擋件）——
`AppShell` 的 icon／分組小標與 `EmptyState` 的 avatar icon 原本各自貼補丁做同一件事，
2026-07-24 已收進 token 並移除，視覺不變。

**為什麼需要**：極光背景層是 `fixed inset-0`，**亮光帶永遠釘在畫面上方三分之一、不隨捲動離開**，
所有內容都會從它底下經過——那正好是閱讀時視線停留的位置，不是「頁面頂端的一小塊」。
掃描（動畫取峰值、含毛玻璃 24px blur、扣掉 header 的內容區）：

| 文字階 | 改前（玻璃 38%） | **改後（玻璃 45% ＋ 半階）** |
|---|---|---|
| highlighted | 4.21／1.8% | **4.98／0%** |
| default | 3.32／4.4% | 3.93／3.1% |
| toned | 2.85／8.0% | 3.37／4.8% |
| **muted** | **1.61／22.1%** | **2.56／10.3%** |
| dimmed | 1.00／100% | 1.42／28.2% |

**單靠玻璃不透明度救不了**——達 4.5 所需的最低不透明度：white 41%／default 51%／toned 57%／
**muted 80%**／**dimmed 即使 100% 也不夠**（`neutral-500` 對 `neutral-900` 本身只有約 3.0）。
80% 等於看不見星空，主題就白做了。**玻璃的邊際效益也很低**：對 muted 而言
45%→10.3%、55%→6.9%、60%→4.5%。真正把 muted 從 22% 拉下來的是文字階提亮，不是玻璃。

> **刻意接受的例外**：最亮光帶上 `muted` 仍有約 10% 面積、`dimmed` 約 28% 面積低於 AA 4.5。
> 那是半透明玻璃壓在發亮漸層上的固有結果。
> `dimmed` 與 §2.7 既有的 dimmed 例外同一條理由：限最弱提示、**不得承載必要資訊**。
> 日後若覺得亮帶處仍糊，下一個有意義的點是玻璃 **55%**（`toned` 降到 1.8%、`muted` 6.9%），改一個數字即可。
>
> ⚠️ **層次與對比在這裡是直接的取捨**：提整階讓 muted 只剩 4.6% 不過標，但會與 toned 撞色、
> 損失一階層次。2026-07-24 Steven 拍板**要層次**，接受 muted 的 10.3%。

> 附帶：`--aurora-panel` 原本的 38%（2026-07-24 改 45%）**不是為這片極光調的**——2026-07-16 從另一個專案
> my-apps 的 `AppPageLayout glass` 直接沿用。所以它沒有「原本的理由」需要保護。

## 10. 文案與格式

### 10.1 日期與時間

畫面上一律 **`2026/07/17`（斜線、補零）** 與 **24 小時制 `15:04`**；秒數只給稽核日誌。
**唯一出口＝`shared/lib/datetime.ts`，不要在頁面裡自己寫格式化。**

| 用途 | 函式 | 樣子 |
|---|---|---|
| 純日期欄位（到職日） | `formatDate` | `2026/07/17` |
| 時間戳只要日期那面 | `formatTimestampDate` | `2026/07/17` |
| 時間戳（最後登入） | `formatDateTime` | `2026/07/17 15:04` |
| 稽核日誌 | `formatDateTimeWithSeconds` | `2026/07/17 15:04:05` |
| 表單預填今天、匯出檔名 | `todayIsoDate` | `2026-07-17`（ISO，非顯示用） |

理由：**斜線**貼齊同事的 Excel/科威/政府系統；**補零**是為了對齊（顯示日期的欄位一併加 `tabular-nums`，等寬數字才真的對齊）；**24 小時制**避免「上午 12 點」的歧義；**不用民國年**（排序、比對、匯入都會多一層換算）。

**三條硬規則**（都是踩過的坑）：

1. **資料層維持 ISO，只有送到人眼前的最後一哩才轉。** 資料庫、API、`DateInput` 的 `v-model`、匯出檔名一律 `YYYY-MM-DD`。
2. **「純日期」不准經過 `new Date()`。** `new Date('2023-09-23')` 是 UTC 午夜，換算回當地會變前一天。所以 `formatDate` 與 `formatTimestampDate` 是**兩個不同的函式**。
3. **要「今天」就用 `todayIsoDate()`，不要 `toISOString().slice(0,10)`。** 後者是 UTC 的今天，台灣 00:00–08:00 之間會少一天。後端用 `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Taipei' })`（不依賴容器時區）。

> **「存的值 ≠ 使用者選的值」時，換算必須是唯一一份。** 角色到期日存「隔天 00:00」，顯示要換算回「最後有效那天」——曾因兩頁各自換算而差一天。

### 10.2 用字

- **第二人稱一律「您」**（後端信件範本本來就是）。程式註解不受此限。
- 回應與文件輸出使用**繁體中文（台灣用語）**。

### 10.3 通知內容規範（收件匣＋Email 共用，2026-07-24 定）

> 每種通知的文字都照同一套文法填，未來新事件照套即可。權威＝後端註冊表
> `apps/api/src/core/notifications/notification-registry.ts`（每筆事件一組 `category`／`title`／`body`）。
> 收件匣（`NotificationPanel.vue`）與 Email 眉標（§11.3）**吃同一份**，不各寫一套。

**三個語意欄位：**

| 欄位 | 是什麼 | 規則 |
|---|---|---|
| **類別** | 這是哪種通知 | 短、結尾一律「通知」；**註冊表 `category` 是單一來源**，收件匣第一行＝Email 眉標同字。**與偏好分組脫鉤**（行事曆提醒掛 ACCOUNT 分組收偏好，但類別是「工作日曆通知」）。 |
| **標題** | 一句「發生了什麼」的短事實 | 單行、不塞會爆長的細節。**語態跟收件人走**：通知關於**別人**→第三人稱事實（`王小明 已到職`）；關於**您自己**→第二人稱「您」（§10.2）（`您的帳號角色已變更`）。 |
| **內文**（可選） | 補充：影響／要做什麼／安全提醒 | 標題放不下的細節下放到這；沒有就不給。 |

**踩過的坑（這規範解掉的）：**

1. **類別雙頭**：曾經收件匣用前端字典、Email 用分組名各推一套——行事曆提醒收件匣顯示「管理中心通知」、Email 顯示「帳號與安全通知」，同一封信兩個名字。收斂成註冊表 `category` 單一來源。
2. **標題爆長換行**：`${姓名} ${summary}` 一長就撐到第二行。規範：標題只放短事實，細節進內文（如職務異動：標題 `王小明 職務異動`＋內文 `職稱調整為 資深專員兼專案經理`）。

**現行 6 種通知（範例對照）：**

| 事件 | 類別 | 標題 | 內文 |
|---|---|---|---|
| 到職 | 人事異動通知 | 王小明 已到職（2026-08-01） | 公司／部門 |
| 職務異動 | 人事異動通知 | 王小明 職務異動 | 職稱／調動細節 |
| 離職 | 人事異動通知 | 王小明 已離職（2026-08-01） | — |
| 角色調整 | 帳號安全通知 | 您的帳號角色已變更 | 由管理員調整，可至個人資料頁查看目前權限。 |
| 行事曆提醒 | 工作日曆通知 | 2027 年政府行事曆尚未匯入 | 下載＋匯入指引 |
| 密碼重設 | 帳號安全通知 | 管理員已為您寄出密碼重設連結 | 安全提醒 |

> **敏感細節鐵則（不變）**：`title`／`body` 只准寫「誰、什麼異動、什麼時候」，禁止夾離職原因、薪資、考核等——
> Code Review 擋件（見註冊表檔頭 Rule 8）。離職通知刻意無 `body`＝結構上就沒地方塞敏感欄位。

**新增通知類型的流程（Code Review 擋件，§13-19）：** 任何新增 `notificationRegistry` 事件的 PR，
其 **`category`／`title`／`body` 文案必須先跟 Steven 討論定案**（這類叫什麼、標題怎麼寫），
不可工程師自行命名就合併。理由：這些字是**全體員工會看到的對外文案**，用語一致性與親和度是
Steven 的決策範圍（同「面向全員的文案／命名先拍板」的通則）。流程：開發前把新事件的三格草案
列給 Steven → 拍板 → 才寫進註冊表；PR 描述附上拍板結論供 review 對照。

### 10.4 頁面副標（PageHeader description，2026-07-24）

副標是「這頁大概在幹嘛」的**一句目的提示，不是說明書**。過長的副標在縮小螢幕時會折成 2～3 行、把版面撐歪。

- **一句、單一子句、建議 ≤ 20 全形字**；不要用 `；` 串多個子句。
- **機制／操作說明**（優先順序、停用行為、怎麼查找、匯入步驟）→ 放 **標題旁的 ⓘ／內文／docs**，不塞副標。
- **不放 `共 N 筆` 之類計數**——`TablePaginationFooter` 已顯示總數，副標再放一次是重複。
- **版面**（`PageHeader` 已內建，不用逐頁寫）：`<sm` 手機隱藏；`≥sm` 顯示但 `line-clamp-1`——就算某頁寫太長也只佔一行＋省略號，不會折成一坨。
- 好例：「查看、搜尋、建立與編輯使用者」「集中管理所有模組的權限組合」；壞例：「全平台唯一的『哪天上班』真相：每年匯入政府行事曆，颱風假等突發以覆寫處理；出勤等模組依此判斷工作日。」（已於 2026-07-24 全站收斂）。

> 面向全員的文案，改動照「先跟 Steven 拍板」的通則（同 §10.3）。

#### 10.4.1 hover-only 不得承載「只有這裡看得到」的資訊（2026-07-29 定案）

**觸控裝置沒有 hover。** 只靠 hover 出現的內容，在手機上等於不存在——
iOS 點按鈕甚至不保證給 focus，所以連「focus 也會開」都救不了。

| 內容性質 | 用什麼 | 為什麼 |
|---|---|---|
| **說明性文字**（機制、判準、為什麼不能按） | **點擊開的 `UPopover`** | 兩種輸入都通：滑鼠點、觸控點、鍵盤 Enter；Esc／點外面關 |
| **圖示鈕的名字**（編輯／刪除／查看） | `UTooltip` 可以留 | 它只是把 `aria-label` 視覺化，資訊本來就在別處（圖示語意＋無障礙名稱），手機看不到不損失什麼 |

判準一句話：**這段字是「補一個名字」還是「只有這裡講得到」？** 後者一律不准 hover-only。

`PageHeader` 的 `hint` 已於 2026-07-29 由 `UTooltip` 改為 `UPopover`（一處改、全站頁面生效）。

> 同一個病 §8.1 的停用鈕那段記過一次（停用原因掛 `title`，手機永遠讀不到），
> 當時只修了那一處、沒有升成通則，於是 ⓘ 又犯了一次。這次寫成規則。

**⚠️ 本節的規則綁在 `PageHeader` 元件上，但副標不是只有那裡有**（2026-07-27 補）。
帳號中心各頁、卡片／區塊的 header 都是自己手寫 `<h1>`＋`<p>`，**整條規則管不到**——
於是有的隱藏有的不隱藏、有的截斷有的不截斷、色階也各憑感覺。

**沒走 `PageHeader` 的副標要自己補齊三件事**（色階判準見 §2.5.1）：

```html
<p class="mt-1 text-sm text-muted max-sm:hidden sm:line-clamp-1">…</p>
```

判斷順序：先問這段屬 §2.5.1 的哪一階——**是「必讀」就不適用本節**（它不是副標，
是被塞錯位置的內文，見 §2.5.1 的處理方式）；是「輔助定位」才照上面走。

### 10.5 平台命名（2026-07-24 Steven 拍板）

> 平台對員工有三種寫法，各有各的場合。**定義的權威在 platform repo `CONTEXT.md` 的「產品名」詞條**，
> 本節只管「哪個場合用哪個、什麼不准寫」。

| 寫法 | 用在哪 |
|---|---|
| **Ystravel Portal**（英文字樣） | 登入／忘記密碼／重設密碼頁的視覺區、瀏覽器分頁標題 |
| **永信生活旅遊事業員工入口網**（中文全稱） | 正式落款：登入頁副標、對外公告、未來 Email footer |
| **員工入口網**（中文簡稱） | 日常：內文提及、通知內容、口語 |

- **分頁標題格式 `<頁名>｜Ystravel Portal`**（如 `登入｜Ystravel Portal`）。中文頁名配英文站名是**刻意**的——分頁擠窄時只看得到前段，站名短好辨識（同 `收件匣 | Gmail`）。**這不算「中英混雜」違規，不要來修。**
- **不要在同一塊視覺區給平台第二個類別詞。** 登入頁左側已有「Portal」（主標）與「網站」（副標）；再疊 workspace／gateway／platform 就是三行三個類別詞，讀起來像作者自己也不確定這是什麼。

- 「Portal」**不是** SSO 時代殘留：企業界 Employee Portal 的標準語意就是「員工所有內部功能的統一網站」，不是中轉門；雙軌期（門）與 EIP 退役後（全部功能）兩種形狀都成立。

## 11. 信件版型（Email）

> 信件是**另一個媒介**：後端字串模板、沒有 CSS 變數、沒有 dark mode、客戶端會改寫你的 HTML。
> 本節的規則只管信件，前面章節的 token 與元件規範一律用不上（原因見 §11.5）。
> 2026-07-23 定版，實作在 `apps/api/src/common/mail/`。

### 11.1 四級顏色（頂條＋眉標＋按鈕同一色）

**顏色編碼「收件人該有什麼反應」，不是「哪個模組寄的」**——模組資訊已經由眉標文字表達，
顏色再講一次等於浪費一個維度。

| 頂條色 | 語意 | 對使用者的意思 | 例子 |
|---|---|---|---|
| **teal** `#0d9488` | 週知 | 跟你有關的事發生了，**你不用做什麼** | 人事異動、公告 |
| **藍** `#2563eb` | 待辦 | **需要你動手**完成一個動作 | 密碼重設、邀請開通、待審批 |
| **amber** | 提醒 | 有時限、快來不及了，但**還沒出事** | 審批逾期、連結即將過期、額度將滿 |
| **rose** | 警示 | **已經出事**，或涉及帳號安全 | 異常登入、權限遭變更、匯入失敗 |

三條規則：

1. **一封信只有一個顏色**：頂條、眉標、按鈕、內文連結全部同色。
2. **rose 要稀有。** 什麼壞事都用紅色＝紅色不再有意義。判準是「使用者**忽略**這封信會不會有實質損失或安全風險」——不會就降級 amber。
3. **顏色不是唯一線索。** 色盲、以及部分客戶端會改寫色彩，所以**眉標文字必須單獨就講得清楚**，不能靠顏色補語意。

> amber 與 rose 尚無真實信件使用，色值等第一封落地時比照 §2.2 的 warning／error 家族定。

4. **設計 token 用不到**：色值必須寫死十六進位。**改平台主色時要回來同步這份規範**，信件不會自動跟著變。
5. **驗收一定要真的寄一封。** 預覽頁驗不到 CID logo，也看不出各客戶端差異。

| 用途 | 位置 |
|---|---|
| 全站 Nuxt UI theme 覆寫（含 primary、各元件 slots） | `apps/portal/vite.config.ts` → `ui({ ui: { ... } })` |
| 全域 CSS（字體、圓角基準、layout token、語意色階、aurora token） | `apps/portal/src/assets/css/main.css` 的 `@theme` / `:root` / `.dark` |
| 頁面局部微調 | `.vue` 的 `size` / `:ui` prop / `class` |

**五條施工紀律**：

1. **`vite.config` 是 build-time，不吃 HMR。** Vite 偵測到它變動會**自動重啟** dev server，
   但重啟需要時間——**改完立刻重新整理常常會拿到舊的 theme**（2026-07-28 為此誤判過一次，
   以為覆寫沒生效）。判準：改完 `vite.config` 後量到的值與預期不符，先再 reload 一次再懷疑寫法。
2. **覆寫主題前先讀 `node_modules/.nuxt-ui/ui/<component>.ts` 確認 class 在哪一層**，放同層才贏；覆蓋互動元件底色要連 hover/active/focus-visible 一起蓋。
3. **`vite.config` 的 `ui` 設定裡同名 key 會整個蓋掉，而且是靜默的。** 看到 TypeScript 的 `TS1117`（duplicate key）**不要只改名字閃過去，要把兩個區塊合併**。
4. **覆寫 `variants.*` 前先確認該變體的值是「字串」還是「物件」——同一個元件的不同區塊可以不同。**
   badge 的 `compoundVariants` 吃字串，但 `variants.size` 吃 `{ base: '...' }`；寫成字串會把官方
   那一整組（字級／內距／圓角）**整個換掉**而不是附加，class 裡出現字面的 `[object Object]`。
   **typecheck、build 全都不會報錯**，而且你想改的那個屬性（圓角）確實會生效，只有其他屬性悄悄消失。
   > **連帶的驗證紀律：覆寫任何共用層設定後，不要只量你想改的那個屬性。**
   > 先問「這個變體／這個 slot 原本還帶了什麼」，再把那些一起量一次
   > （2026-07-28 只驗圓角、漏掉字級與內距，是 Steven 從畫面上看出來的）。
5. **改「尺寸／間距」類的值之前，先確認官方把它寫在 `slots` 還是 `variants.size`。**
   這是第 2 條的具體化，但值得單獨列出來，因為**它的失敗症狀是「部分生效」而不是「沒生效」**。

   官方常把同一個 slot 的**外觀**放 `slots`、**尺寸相關**（icon 大小、內距、間距、字級）
   放 `variants.size.<階>`。變體贏 slots，所以寫錯層的東西會被靜默蓋掉：

   | 你寫在 slots 的 | 官方在 `variants.size.md` 的 | 結果 |
   |---|---|---|
   | `itemLeadingIcon: 'size-4'` | `itemLeadingIcon: 'size-5'` | **完全沒效**（icon 一直是 20px）|
   | `empty: 'p-2'` | `empty: 'py-6 text-sm'` | **只有左右生效**——`py-6` 沒被覆蓋，上下紋風不動 |

   第二列才是危險的：畫面**確實變了**，所以你會以為改成功、不會再去量。
   2026-07-29 做頁面搜尋時兩種都踩到，而且是**踩了第一種、寫了註解警告、十分鐘後踩第二種**。

   > **判準：改完之後量的是「你想改的那個方向」，不是「有沒有變」。**
   > 想改上下內距就量上下，不要看到左右變了就收工。

37. 骨架屏直接鋪在頁面底上（沒有卡片外殼）——淺色下 `bg-elevated` 與 `--app-surface-page`

38. icon 尺寸憑感覺挑，沒照 §6.5.1 的結構角色（單行同列 16／多行區塊與獨立圖示 20／

    toast 縮 icon 時前導 icon 與關閉鈕同時偏高 2px，而那不會有任何東西報錯（見 §6.5.1）
39. 寫 `rounded-[任意值]` 繞過圓角刻度（唯一例外＝巢狀圓角，且要在原地寫明理由）；
    或**在使用點貼 class 蓋掉元件預設**而不是回頭改該元件的 theme——同一個補丁抄超過
    兩三次就是預設值錯了，2026-07-28 為此清掉 61 處（見 §4.2）。
    ⚠️ **`rounded-xsm`（半階 3px）是刻度的一部分、不是任意值**，巡檢時不要「順手統一」掉；
    也要注意在使用點蓋徽章／xs 控件的圓角會**靜默失效**（tailwind-merge 不認得半階，見 §4.2）
40. 覆寫元件 theme 的 `variants.*` 時**沒確認該變體的值是字串還是物件**：badge 的
    `variants.size` 是 `{ base }`，寫成字串會把官方那一整組（字級／內距／圓角）**整個換掉**，
    class 裡出現字面的 `[object Object]`，而 typecheck、build 全都不會報錯（見 §12）
41. **說明性文字掛在 hover-only 的 tooltip／`title` 上**——觸控沒有 hover，
    手機使用者永遠讀不到（iOS 點按鈕連 focus 都不保證給）。圖示鈕的名字可以留 tooltip
    （它只是把 `aria-label` 視覺化），**「只有這裡講得到」的內容一律改點擊開的 popover**（見 §10.4.1）
42. 新增可點的清單列（選單項目、下拉選項、自刻的列表），**在手機沒有 40px 高**；
    或把觸控目標規則寫進 `size` 變體而非 `item` slot（等於宣告「小尺寸控件的選項可以難點」）；
    或**只放大觸發器不放大選項**——同一顆控件套一半的規則最難察覺，因為「有訂規則」
    這件事會讓人不再去量（見 §4.5.1）
43. 覆寫元件 theme 的**尺寸／間距**（icon 大小、內距、間距、字級）時**沒確認官方
    寫在 `slots` 還是 `variants.size`**：變體贏 slots，寫錯層會被靜默蓋掉。
    危險的不是「完全沒效」（那你會去查），是 `p-2` 蓋 `py-6` 這種**只有左右生效**
    ——畫面確實變了，於是收工。**改完要量「你想改的那個方向」，不是「有沒有變」**（見 §12-5）
44. 寫死 px 字級（`text-[15px]`）**沒帶 `var(--fs)`**（見 §3.4）。它在標準檔完全正常，
    只有使用者把字級調大時才會露出「全站只有這一處沒放大」——**你不會在開發時發現**
45. **`ghost`／`outline` 控件直接坐在頁面底上**（`PageHeader #actions`、任何不在卡片裡的位置）
    **卻用官方預設的 `hover:bg-elevated`**（見 §2.4.1）。light 下 `bg-elevated` ＝
    `--app-surface-page`，hover 前後**逐位元同色**。要 `hover:bg-accented`，且只改 light。
    ⚠️ **typecheck、build、單元測試全都會過**，dark 也完全正常——這個洞只在淺色露出來
46. **拿 `bg-accented`（選取態那一階）當 hover 用**（見 §2.4.2）。hover 的階要看選取態
    佔了哪一階：選取態走灰階 → hover 用半階 `elevated/50`；選取態走品牌色或沒有選取態
    → hover 用整階 `elevated`。⚠️ **改任何一個狀態的色階之前，先把同元件的其他狀態一起列出來**
    ——只看 hover 就把側欄提到整階，會讓 hover 與 active 撞色
47. **「（選填）」寫在有欄位標題的地方**（見 §6.2.1）——同表單已有紅星可對比時再寫一次是重複；
    反過來，**一整列沒有標題的可增刪列表（聯絡方式、樓層資訊）漏了必填標示**也擋：
    那裡星號無處可放，必填要寫在區塊標題下方一行說明，**不要塞 placeholder**
    （塞不下，而且「電話與傳真擇一」這種跨欄位規則本來就不是單格講得完的）
48. **帶框容器裡最後一項也畫下框線**（見 §5.5.1）——會與外框下緣疊成一條 2px 粗線
    （實測間距 `0.00px`）。線只畫在項目與項目之間；後面接說明段時由說明段自帶 `border-t`。
    ⚠️ 兩欄版的「最後一列」可能是左右兩格，`last:` 抓不到左邊那格；`<sm` 單欄時又只有
    `last:` 是對的——要算視覺列索引，別只寫一個 `last:` 就收工
49. **用「間距的不對稱」表達語意分層**（2026-07-31）——同一張卡裡兩個**視覺重量相同**的區塊
    （同圓角同邊框同底色），間距一大一小會讀成「一塊被切開」，不會讀成你想表達的因果。
    卡內區塊間距一律沿用既有節奏（`TableCard` 是 20px），**要為新區塊發明第三個間距值之前，
    先問這頁憑什麼跟別頁不一樣**
50. **卡內的帶框容器圓角沒照「內圈比外圈小一階」**（見 §4.2.1）——內外同階＝差 0，
    畫面上看不出那是內縮區塊。⚠️ 反過來也擋：**看到多種圓角就想「統一成同一個值」**
    ——先量外圈，多半是照外圈推導的正確規律
51. **寫「規範沒定所以維持現況」的註解或測試，卻沒真的去查規範**（見 §5.7 空值那條）。
    斷言現況的測試會讓後來改對的人看到紅燈，**於是以為現況才是對的**——
    比沒有測試更糟。真的沒定就當場定，不要用測試把違規焊死
52. **列內操作欄常駐超過 3 顆 icon 鈕**（見 §5.4.2）——第 4 顆起要收進 `RowActionsMenu`，
    而且**收就收到只留最常用的一顆**在外面（3 顆＋`⋯` 跟 4 顆全攤在寬度上沒有差）。
    ⚠️ 同時擋**把不能用的動作放進選單再 disable**：點不下去的項目會被當成壞掉，該整條不放
53. **新列表頁的篩選條件 ≥ 3 卻沒接「我的篩選」**（見 §5.3.2）——那正是「每天重選同一組」
    會發生的門檻。⚠️ **反過來也擋：條件只有 1–2 個卻硬接**——開清單挑一組要兩個動作，
    比直接點那一兩個下拉還慢，等於在頁面上放一顆沒人會按的鈕，而這種鈕之後最難拿掉。
    ⚠️ 也擋**對員工把它叫成「常用篩選」**：系統沒有在計算使用頻率，
    而「我的」同時把「只有你看得到」講清楚了（見平台 `CONTEXT.md`）
54. **半透明底色的元素直接坐在極光背景上**（見 §5.2.2）——`bg-{色}/10` 這類元素
    需要一層不透明或高不透明度的底才顯得出來，而**極光是漸層**（同一頁上方亮、下方暗），
    所以它清不清楚**取決於落在頁面哪個位置**，不是一個可以調的數字。
    ⚠️ **淺色與一般深色下這個問題不存在**（那兩者的頁面底是單一色）——
    **只驗淺色一定漏掉它**。2026-08-10 客戶詳情的標籤 chip 就是這樣被發現的
55. **詳情頁識別區的 chip 在手機沒有收合**（見 §5.2.3 ②）——`<sm` 要收成 N 顆＋
    可點的〔⌄ +N〕，`≥sm` 全部顯示。⚠️ **桌機不要收**（三個字級都是 1 排，
    收了等於平白藏資訊），⚠️ 也擋**靜態截斷**（只顯示前 N 顆、其餘看不到）
    ——那種 prop 全站零使用，「看得到但收起來」才是實際需要的行為。
    ⚠️ 切換鈕要**接在 chip 列尾端**，另起一行會自己多佔一排（375px 實測 24px），
    把收合省下來的高度又吃回去
56. **動作鈕與資料 chip 放在同一個 `flex-wrap` 容器**（見 §5.2.3 ③）——要拆成上下兩塊
    （`flex-col gap-3`）。⚠️ **理由不是「長得像」而是「位置不穩定」**：同容器時
    **chip 只有 1～2 顆那顆鈕會真的跑進 chip 那一排**，多了才換行
    ——時而同排時而換行，讀起來就是「第 N 顆 chip」。
    ⚠️ 這一條**桌機也成立**，不是手機專屬

### 13-1 明文例外：登入／忘記密碼／重設密碼三頁的 `!important`

**擋件第 1 條（禁 `!important`）在這三頁不適用**，且**不得援引為其他頁面的先例**。

理由：這三頁有**自己一套 palette**（`--panel-*`／`--button-*`），刻意與全站主題不同——
它們是未登入者看到的品牌門面，不是模組頁。那些 `!important` 是拿頁面變數去蓋
Nuxt UI 的全域 button／input 主題，**覆寫範圍就這三個檔案，不會外溢**。

Steven 2026-07-28 拍板維持現狀，判準是投報比：
- **零功能收益**——它現在完全正常，只是規則書上有個洞
- **驗證成本高**——軌道動畫、極光背景、autofill、Google 鈕、記住我 checkbox，
  每一項都要在明暗兩個主題實測
- **改壞的代價最大**——這是唯一一個「壞掉就沒人進得來」的頁面

技術上做得到零視覺變化（同樣的變數，只是把施加位置從頁面搬到 theme 層）。
**未來真的要改登入頁視覺時再一起收**，不要為了規則單獨動它。

⚠️ 其中 `input:-webkit-autofill` 那組**不算例外、是唯一解**：瀏覽器自動填入是 UA 層樣式，
不加 `!important` 蓋不掉。這條在任何頁面都成立。

> ⚠️ **編號一旦給出去就不要重排。** 2026-07-27 發現 28～30 重複了兩組
> （新加的一組插在舊的上面、各自從 28 起算），修正時把**後面那組**推成 31～33。
> 新增條目一律**接在最後**，不要插隊——這份清單的編號是它被引用的方式
> （PR 描述、`ui-conventions.md`、本檔內部交叉引用都指編號）。
